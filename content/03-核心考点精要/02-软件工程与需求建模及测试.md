# 软件工程与需求建模及测试

本篇为 AI 辅助整理的非官方学习手册。概念采用教材归纳与明确标出的工程补充；口诀、例题、答案及作答模板均为教学归纳，不是官方答案或真实项目事实。优先级是学习安排，样本考频不代表未来命题概率。

## 学习范围与优先级

优先级 P0。2023 年起仓库五场考试的主主题统计：综合知识 71 题、案例 3 道大题、论文 4 题。每题只归一个主主题；组内粒度不同，计数不代表单考点概率或预测分值。具体题号与分年结果见[样本记录](../../verification/核心考点精要-考频样本.md)，覆盖边界见[覆盖表](11-大纲与教材考点覆盖表.md)。

## 五分钟速记

- 螺旋模型以风险分析为突出特征；RUP 是用例驱动、架构中心、迭代增量。
- RUP 四阶段：初始、细化、构造、移交；确定架构重点在细化阶段。
- 需求开发：获取、分析、规格说明、验证；需求管理贯穿跟踪与变更。
- DFD 看数据如何流动和加工；流程图看控制流程；UML 各图各有关注点。
- 黑盒按规格设计；白盒按内部结构设计；静态测试不运行被测程序。
- 测试发现问题和提供质量证据；调试定位与修复原因。测试不能证明没有缺陷。

## 1 过程模型与成熟度

| 模型 | 适用线索 | 代价或易混点 |
|---|---|---|
| 瀑布 | 需求相对明确、阶段交付物清晰 | 需求变化晚发现时返工成本高 |
| 原型 | 用户需求不清，需反馈澄清 | 原型不一定直接演化成最终产品 |
| 增量 | 分批交付可用功能 | 提前考虑整体架构及集成 |
| 螺旋 | 大规模、高风险、迭代中显式分析风险 | 管理及风险分析成本较高 |
| 敏捷 | 短周期交付、持续反馈、适应变化 | 不等于不写文档、不做设计 |
| RUP | 用例驱动、架构中心、迭代增量 | 四阶段均可能含多个工作流，不能当成四个单一活动 |
| 净室 | 形式化规约、正确性验证、统计质量控制 | 不是取消测试，而是强调预防缺陷与统计测试 |

RUP：初始确定范围与商业可行性；细化稳定架构、降低关键风险；构造实现可交付产品；移交部署给用户。

教材所用 CMMI 阶段式成熟度：1 初始级 → 2 已管理级 → 3 已定义级 → 4 量化管理级 → 5 优化级。2 关注项目管理，3 关注组织标准过程，4 关注量化，5 关注持续改进。不要将旧 CMM 的“可重复级”等名称混进来；产品版本题按题设。

Scrum 的辨认抓手是固定长度迭代、产品待办列表、每日沟通与明确职责；产品负责人关注价值和待办排序，Scrum Master 帮助团队有效使用 Scrum，开发者交付增量。XP 关注结对编程、测试先行、持续集成、重构等工程实践；看板关注可视化流程与限制在制品。

## 2 需求工程与跟踪

| 对象 | 回答什么 | 自编示例 |
|---|---|---|
| 业务需求 | 为什么建设 | 降低重复录入与审核等待 |
| 用户需求 | 用户完成什么任务 | 采集员提交记录、审核员退回补充 |
| 系统功能需求 | 系统提供哪些行为 | 校验必填项、生成任务编号 |
| 质量需求 | 在什么条件下做到什么程度 | 高峰期 95% 提交两秒内返回 |
| 约束 | 必须遵守的边界 | 采用既有统一身份认证平台 |

获取方法：访谈、问卷、观察、研讨会、原型、现有文档分析。验证检查正确性、完整性、一致性、可行性、无歧义与可验证性。

双向跟踪：从需求追踪到设计、代码和测试，确认实现覆盖；从实现或测试追踪回需求，避免无依据功能。变更应记录申请、影响分析、决策、基线更新与验证，不能只改代码。

自编案例答法：若频繁返工源于需求歧义，先建立术语和可验收标准，用原型澄清，再建立基线、跟踪矩阵和变更机制；“加强沟通”不足以说明如何执行。

## 3 结构化分析与 UML

DFD 四要素：外部实体、加工、数据流、数据存储。上下层数据流图需要保持边界数据流的平衡；数据字典解释流和存储的内容；加工逻辑可用结构化语言、判定表或判定树表示。

| UML 图 | 关注点 |
|---|---|
| 用例图 | 参与者与系统提供的功能 |
| 类图／对象图 | 类型的静态关系／某时刻实例及联系 |
| 顺序图 | 对象间消息的时间顺序 |
| 通信图 | 对象协作与消息连接关系 |
| 活动图 | 工作流、分支、并发、泳道职责 |
| 状态图 | 对象随事件变化的状态与转移 |
| 构件图 | 构件及其依赖 |
| 部署图 | 软件制品映射到节点的部署关系 |

泛化表示“是一种”；关联表示结构联系；依赖表示使用关系；实现表示符合接口契约；聚合与组合都是整体—部分，组合强调更强的所有权和生命周期约束。

用例 include 表示纳入可复用的行为；extend 表示在条件满足时增加扩展行为。活动图的分叉／汇合用于并发，决策／合并用于条件路径，不能互换。

内聚由强到弱的常见教材序列：**功能、顺序、通信、过程、时间、逻辑、偶然**。顺序内聚是前一步输出成为后一步输入；通信内聚是多个操作围绕同一输入或输出数据；功能内聚围绕一个明确功能。

扇入是调用本模块的模块数量；扇出是本模块直接调用的下级模块数量。不要以扇入、扇出单独判定系统质量。

耦合辨认：数据耦合传必要数据；标记耦合传整个结构而只用部分；控制耦合传控制标志；公共耦合共享全局数据；内容耦合直接依赖或修改另一模块内部实现。总体目标是降低不必要的依赖。

## 4 设计模式快速辨认

| 类别 | 模式与主要意图 |
|---|---|
| 创建型 | 单例：控制实例；工厂方法：延迟具体创建；抽象工厂：创建相关产品族；建造者：分步构造；原型：复制已有对象 |
| 结构型 | 适配器：转换接口；桥接：抽象与实现分离；组合：树形整体与部分；装饰器：动态增加职责；外观：统一入口；享元：共享细粒度对象；代理：控制访问 |
| 行为型 | 策略：替换算法；状态：状态变化驱动行为；观察者：变化通知；命令：封装请求；责任链：请求沿处理链传递；模板方法：固定骨架与可变步骤；迭代器：遍历；中介者：集中协调；备忘录：保存恢复；解释器：解释语言；访问者：分离对象结构与操作 |

易混：适配器改变接口；装饰器增加职责；代理控制访问。策略关注可替换算法，状态关注内部状态导致的行为变化。微服务是架构组织方式，不能与单个对象层面的设计模式直接等同。

## 5 测试方法、覆盖与性能测试

| 维度 | 辨认 |
|---|---|
| 静态／动态 | 是否运行被测程序 |
| 黑盒／白盒／灰盒 | 是否依据内部结构信息 |
| 单元／集成／系统／验收 | 分别聚焦模块、接口协作、整体系统、用户验收要求 |
| 回归 | 修改后检查原有行为是否受到破坏 |
| 黑盒用例设计 | 等价类、边界值、判定表、因果图、场景、错误推测 |

覆盖标准：语句覆盖让每条可执行语句至少执行一次；判定覆盖让每个判定的真假分支都执行；条件覆盖让基本条件的真假都出现；条件组合覆盖覆盖条件取值组合；路径覆盖针对执行路径，循环会使全路径不可穷举。

**条件覆盖不必然包含判定覆盖，反过来也不必然成立。** 按抽象布尔判定、不考虑短路求值的示例：判定 A 或 B，采用（真、假）与（假、真），各条件真假都出现，但判定始终为真。涉及具体语言时须按短路规则判断实际求值。

工程补充：MC/DC 要体现每个基本条件能独立影响判定结果；圈复杂度常用连通控制流图的 $V=E-N+2$，或二分判定结点数加 1，注意适用图条件。

| 性能测试 | 关注什么 |
|---|---|
| 基准测试 | 固定条件下的性能基线 |
| 负载测试 | 预期业务负载下是否达标 |
| 压力测试 | 超出正常负载后的极限、退化与恢复 |
| 并发测试 | 同时操作带来的锁、竞态、争用 |
| 稳定性／耐久测试 | 长时间运行后的泄漏和性能退化 |

性能测试按“目标与负载模型—环境与数据—监控与基线—执行—瓶颈分析—同条件回归”闭环。同时看成功率、吞吐量、P95/P99 响应时间、资源使用和队列积压；平均响应时间不能代替尾延迟。

## 6 项目与配置管理

范围、时间、成本与质量相互制约；风险应识别、分析、制定应对并持续监控。配置项是受控对象；基线是经过正式确认的版本；变更控制、版本管理、配置审计不是同一件事。

工程计算补充：挣值 EV 是已完成工作的预算价值，PV 是计划工作的预算价值，AC 是实际成本。$CV=EV-AC$，$SV=EV-PV$，$CPI=EV/AC$，$SPI=EV/PV$。CPI 小于 1 表示成本效率低；SPI 小于 1 表示按预算价值计进度落后，不能直接等同于落后多少天。

## 自编自测与参考答案

1. RUP 哪个阶段重点确定架构？——细化阶段；不是等全部代码完成后再决定。
2. 修改功能但没有新增回归测试，有何风险？——原有功能受影响而未被发现；建立需求到测试的跟踪并执行相关回归。
3. 先判断 A 或 B，两组用例真假／假真能否判定覆盖？——不能，判定没有出现假。
4. 一个包装对象保持接口并附加日志能力，优先联想到什么？——装饰器；仍需根据意图区别代理。
5. EV=80、PV=100、AC=90，状态如何？——CV=-10、SV=-20，CPI≈0.89、SPI=0.8，成本和进度表现均不理想。
6. 代码包组织与消息时间顺序分别看什么？——前者可看包／开发组织，后者看顺序图；不要把部署图当顺序图。
7. 样本练习：2025 上综合 18–29、49–55、67；2025 下综合 44、49–51、69–70、75。答案存在争议时回到概念，不机械记选项字母。

完成标准：能从场景选模型、区分 UML 图、解释覆盖关系，并写出需求或测试问题的具体改进闭环。

## 补强：构件组装与复用

教材归纳：CBSE 把重点从逐个实现功能转向选择、适配和组装构件。按教材口径记五个特征：可组装、可部署、文档化、独立、标准化；模型约定接口、使用信息和部署，基础设施提供平台服务及通用支持服务。具体工程中的构件交付形式不能全部限定为某一种二进制格式。

| 组装方式 | 机制 | 接口检查 |
|---|---|---|
| 顺序 | 依次执行，前一构件输出作为后一构件输入 | 数据格式、单位、异常能否衔接 |
| 层次 | 一个构件调用另一个构件的服务 | 提供接口是否满足请求接口 |
| 叠加 | 合并多个构件功能，统一提供新接口 | 功能组合与对外契约是否一致 |

参数不兼容指同名操作的参数数量或类型不匹配；操作不兼容指操作名称不一致；操作不完备指所需操作集合未被完整满足。适配器可协调接口，但不能仅改名字就补出缺失的业务能力。

CBSE 基本过程：概览需求→识别候选构件→协商调整需求→设计架构→定制适配→组装系统。不能为了迁就现成构件擅自取消用户的关键约束。

## 补强：UML 与形式化建模

| 元素 | 准确含义 | 易混点 |
|---|---|---|
| 参与者 | 系统边界外与系统交互的角色 | 不是所有业务名词都要画成参与者 |
| 实体类 | 保存领域信息和业务状态 | 不要求与数据库表一一对应 |
| 边界类 | 与人员或外部系统交互的边界 | 不承担全部业务规则 |
| 控制类 | 协调一个用例或过程 | 不应无条件成为全系统巨型控制器 |
| include | 基础用例包含可复用行为 | 箭头从基础用例指向被包含用例 |
| extend | 在条件和扩展点下增加行为 | 箭头从扩展用例指向被扩展用例 |
| 泛化 | 更特殊角色或类型继承一般者特征 | 空心三角指向一般者 |

顺序图先列生命线，再按时间顺序列消息、执行片段和守卫条件。同步调用要等待返回；异步发送不要求调用方等待；返回消息表示结果返回。自调用说明发送者与接收者相同，是另一分类维度，不能与同步、异步误当互斥选项。

组合片段：alt 表示条件分支；opt 表示可选执行；loop 表示循环；par 表示并行；break 表示中断余下交互。通信图强调对象间连接与消息编号，顺序图强调时间次序。题目没有给图时只分析文字约束，不能凭空恢复原图空号。

形式化方法用数学模型与精确定义的规则表达和验证性质；模型检测遍历有限状态模型检查性质，定理证明通过逻辑推导证明性质。它们的结论受模型与假设限制，不能据此保证真实系统没有任何缺陷。Petri 网用库所、变迁、有向弧和标识表达并发：输入库所具有足够托肯时变迁可使能，发射消耗输入托肯并产生输出托肯；是否有界、可达、活性等需要根据具体网分析。

自编练习：服务 X 请求 save、load，构件 Y 只提供 save，属于什么问题？答案：操作不完备；仅增加参数转换不能实现 load。若“支付成功才发货”，应在顺序图中用条件片段或相应守卫表达，不能画成无条件调用。

## 补强：测试用例与项目控制

等价类把输入划为预期处理相同的集合；边界值检查区间端点及相邻值；判定表表达条件组合与动作；状态迁移测试覆盖状态、事件、守卫与转换。自编例：整数输入允许 1～100，边界候选包括 0、1、2、99、100、101；还需按接口约束考虑空值和非整数。

回归测试检查变更是否破坏原有行为；确认测试检查修复是否解决原缺陷。桩模拟被调用模块，驱动模拟调用方。测试结论需要预期结果和断言，覆盖率高并不等于所有业务行为正确。

配置管理包括配置项识别、版本与基线、变更控制、状态报告和配置审计。CCB 决定是否接受受控变更；项目经理安排获批变更的实施。风险管理按识别、分析、应对、跟踪组织；不能把已经发生的问题当作尚未发生的风险。

## 补强：净室的适用边界

教材归纳：净室强调形式化规约、正确性验证、增量开发与统计测试。它要求较强数学基础和专门训练，验证可能耗时；不依赖传统模块调试的开发方式也不能消除语言、编译器、操作系统与环境引入的风险。不要把“净室”理解为不需要测试，统计测试仍承担可靠性评价等任务。

## 补强：软件质量保证

教学归纳：质量保证关注开发过程和活动是否遵循约定规范，通过评审、审计、报告不符合项和跟踪整改建立过程信心；质量控制关注产物及检测结果。测试是质量活动的一部分，不能代替全部质量保证。过程成熟度评价与某个软件产品的质量证明也不是一回事。
