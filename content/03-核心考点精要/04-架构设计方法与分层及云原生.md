# 架构设计方法与分层及云原生

本篇为 AI 辅助整理的非官方学习手册。概念采用教材归纳与明确标出的工程补充；口诀、例题、答案及作答模板均为教学归纳，不是官方答案或真实项目事实。优先级是学习安排，样本考频不代表未来命题概率。

## 学习范围与优先级

优先级 P0。2023 年起仓库五场考试的主主题统计：综合知识 44 题、案例 3 道大题、论文 5 题。每题只归一个主主题；组内粒度不同，计数不代表单考点概率或预测分值。具体题号与分年结果见[样本记录](../../verification/核心考点精要-考频样本.md)，覆盖边界见[覆盖表](11-大纲与教材考点覆盖表.md)。

## 五分钟速记

- ABSD 三基础：功能分解、用架构风格实现质量与商业需求、软件模板。
- ABSD 六子过程：需求、设计、文档化、复审、实现、演化。
- DSSA：领域分析产出领域模型，领域设计产出领域架构，领域实现形成可复用资产。
- SOA 角色：服务提供者、请求者、注册中心；发布、发现、绑定调用。
- SOAP 传消息，WSDL 描述接口，UDDI 支持注册发现，BPEL 编排业务流程。
- 云原生不等于把原程序搬上云；微服务不是拆得越小越好，Serverless 也不是没有服务器。

## 1 方法、复用与领域设计

ABSD 由商业、质量和功能需求共同驱动；允许在需求仍在逐步明确时开始设计，但需求获取不能停止。过程是自顶向下、递归细化和迭代。

ADD 以架构驱动因素尤其质量属性推动分解：选择待分解元素，考虑需求约束与策略／模式，定义职责与接口，再验证。它与 ABSD 有关联，但不能仅凭缩写当成同一个过程。

| DSSA 活动 | 主要产出 |
|---|---|
| 领域分析 | 边界、共同与可变需求、领域模型 |
| 领域设计 | 适应一类系统的特定领域架构 |
| 领域实现 | 按模型与架构组织的可复用资产 |

领域专家提供业务知识；分析人员建立领域模型；设计人员建立架构；实现人员构造可复用资产。软件产品线关注共性与可变性，领域工程建设共用基础，应用工程形成具体产品。

工程补充：DDD 的限界上下文给领域模型规定适用边界，避免同一术语在不同业务中含义混乱；实体强调身份，值对象强调取值，聚合用聚合根维护内部一致性。限界上下文是划分服务的参考，不是必须一对一机械变成微服务。

## 2 架构评估进阶

SAAM 过程抓手：场景开发、架构描述、单个场景评估、场景交互、总体评估。直接场景可由现有架构支持；间接场景需修改架构。多个修改场景集中影响同一构件，提示关注职责和耦合。

ATAM 典型九步：介绍方法、介绍商业驱动因素、介绍架构、识别架构方法、生成效用树、分析架构方法、头脑风暴并排序场景、再次分析架构方法、展示结果。记忆为“说明背景—梳理架构—场景排序—分析权衡—报告”。不同教材表述可略有差异，按所问层次答题。

风险是可能使质量目标不能实现的架构决策或假设；非风险是经分析认为能支持相应目标的决策，依赖其分析前提，不是永远没有风险。敏感点和权衡点回查第 01 篇。

场景辨认：用例场景对应典型使用；增长场景描述预期变化；探索性场景用于探索极端变化和架构边界。

CBAM 将场景响应映射到效用，结合场景权重、策略收益与成本比较投资回报。计算时沿用题目给的效用、权重和 ROI 定义，不能把收入、利润和效用值混用。

## 3 分层与表示层模式

层次式设计常分表示、业务、数据访问、数据。业务规则应有清楚归属，不能散落在界面和数据库访问代码中而难以维护；跨层访问需结合架构约束判断。

| 模式 | 主要关系 |
|---|---|
| MVC | Model 管状态与业务，View 展示，Controller 处理输入与协调 |
| MVP | Presenter 负责交互逻辑，View 尽量被动；经典被动视图变体由 Presenter 协调模型访问 |
| MVVM | ViewModel 提供展示状态与命令，通过绑定联系 View |

逻辑层数不是服务器数量。ORM 映射对象与关系数据，但不能免除 SQL、事务、索引和 N+1 查询问题。

## 4 SOA、Web 服务与集成

| 技术或角色 | 职责 |
|---|---|
| SOAP | 消息格式与处理规则，可通过不同传输协议承载 |
| WSDL | 描述服务接口、操作与绑定等 |
| UDDI | 服务注册与发现 |
| BPEL | 组合／编排服务形成业务流程 |
| ESB | 路由、转换、协议适配等集成能力，减少点对点耦合 |
| 服务注册表 | 维护可发现的服务信息，不代替业务执行 |

REST 是架构风格，常用 HTTP 实现；GET 获取、POST 提交处理、PUT 创建或替换目标资源、PATCH 部分修改、DELETE 删除。HTTP 方法的幂等语义与业务实现是否正确仍需分别验证；不要把所有 HTTP+JSON 接口都等同于满足 REST 约束。

SOA 不强制一定采用 ESB；微服务通常强调业务边界、独立部署与自治，不等于所有 SOA 系统的唯一实现方式。

## 5 微服务与云原生

| 能力 | 作用 | 代价或约束 |
|---|---|---|
| 服务发现与配置 | 找到实例、统一配置管理 | 配置变更也需版本与回滚 |
| API 网关 | 入口路由、认证、限流等 | 注意入口瓶颈和高可用 |
| 容器 | 进程隔离与可重复打包部署 | 通常共享宿主内核，不等于完整虚拟机 |
| 编排 | 管理副本、调度、健康状态与发布 | 有状态数据仍需独立设计 |
| 服务网格 | 把部分服务间流量治理移到基础设施 | 增加运维复杂度和资源开销 |
| 可观测性 | 指标看趋势，日志看事件，追踪看调用链 | 采样、关联和敏感信息控制 |
| DevOps／持续交付 | 将构建、测试、发布和反馈连起来 | 工具不代替组织协作和质量约束 |

不可变基础设施通过新实例替换旧实例，避免长期手工修改造成漂移；不意味着业务数据不能变化。

Serverless 常由 FaaS 与托管后端能力协同，适合事件触发和波动负载；需要考虑冷启动、执行时长／资源限制、外部状态、平台绑定及持续高负载成本。自动伸缩不是瞬时、无限、免费的扩容。

工程补充：蓝绿发布保留两套环境后切换流量；金丝雀发布逐步扩大新版本流量；滚动发布逐批替换。数据库变更兼容、回滚路径、观察指标必须与发布策略一起考虑。

## 6 演化与维护

演化需识别变化动因、分析依赖与影响、设计目标状态和迁移路径、验证并持续更新架构文档。逆向工程从已有实现提取更高层理解；再工程在理解基础上重构或改造；重构通常强调保持可观察行为而改善内部结构。

维护类型：纠错性修复缺陷；适应性适应环境变化；完善性改进功能与性能；预防性降低未来维护风险。根据题目中的直接目的判断，不能只凭“修改了代码”分类。

自编案例：某模块更新经常导致全系统联动发布，可考虑按业务边界调整职责和接口、减少共享内部数据、补契约测试和独立部署流程；同时评估分布式调用与事务成本。不能仅回答“改微服务”。

## 自编自测与参考答案

1. ABSD 是否必须等全部需求固定才开始？——不必，但需求工作与设计并行且需保持可追踪。
2. 领域分析与领域设计产出分别是什么？——领域模型、DSSA。
3. SOAP、WSDL、UDDI 各负责什么？——消息、描述、注册发现。
4. 增加一个云服务器就成为云原生吗？——不能，需看部署、弹性、治理、自动化及可观测等设计。
5. 以缓存旧结果降低响应延迟有什么代价？——数据新鲜度下降，涉及质量权衡；需说明可接受范围。
6. 请求保持不变，仅改善内部结构是什么？——若可观察行为保持，属于重构；业务改变则不只重构。
7. 样本练习：2025 上综合 21、30、35–36、59、65–66；2025 下综合 11–13、23、36–37、40、60、66；下半年案例四与论文一。

完成标准：能区分方法、风格、模式与产品；能围绕业务边界和质量目标说明选型，而不堆缩写。

## 补强：ABSD、复用与模型驱动

ABSD 需求获取关注质量目标、商业目标及开发组织的相关目标；识别构件可按生成类图、分组、打包并明确接口推进。文档化产生架构规格说明和用于检验质量需求的质量设计说明书；复审要引入独立视角，不能只靠设计者自证。实现时先分析设计、组装构件，再进行集成与测试。

教学归纳：复用不是复制代码。机会复用是发现可用资产后采用；系统复用是在开发前规划共性资产。对象可以是需求、架构、构件、模型、测试、过程工具及经验。过程为构造或获取→分类检索与管理→按需求定制、组装和使用。横向复用跨领域通用能力，纵向复用面向特定领域或产品家族。

DSSA 建立过程：界定领域范围→识别领域元素→确定设计实现约束→建立领域模型与架构→产生或收集可复用单元。过程可迭代、并发、递归，不应机械理解为一次性瀑布。三层模型按教材区分领域开发环境、领域特定应用开发环境和应用执行环境。

工程补充：MDA 以平台无关模型 PIM 表达业务结构和行为，按映射规则形成平台相关模型 PSM，再生成或指导实现；CIM 用于更上游的问题与业务语境表达。需要管理模型、转换规则、生成器与手工扩展点，并验证转换前后的约束。MDA 不等于画完 UML 后手工随意编码，也不等于每种业务都能全自动生成。参考：[OMG MDA FAQ](https://www.omg.org/mda/faq_mda.htm)。

## 补强：演化分类、步骤与度量

| 演化维度 | 判断依据 |
|---|---|
| 对象演化 | 接口、类型或语义等对象属性变化 |
| 消息演化 | 交互内容、顺序与传递关系变化 |
| 复合片段演化 | 条件、循环、并发等组合交互变化 |
| 约束演化 | 前置后置条件、不变量等约束变化 |
| 设计时／运行前／有限制运行时／运行时 | 修改发生时机与允许运行状态 |
| 静态／动态 | 是否需要停止运行或能在运行中调整架构 |

教材中的 ABSD 演化六步：需求变化归类→制定演化计划→修改、增加或删除构件→更新构件相互作用→构件组装与测试→技术评审。可持续演化要约束成本、进度、风险和影响范围，保持目标一致、模块独立演化、质量向好与标准依从；不能只追逐新技术。

过程已知时逐个中间版本度量；过程未知时先比较前后版本，再分析可能的变化，不能仅由一个指标唯一反推具体改动。教材归一化距离 D=√Σ((a_i−b_i)/(a_i+b_i))² 描述差异大小，分母必须非零；若题目出现零分母，需要先说明该维指标的处理约定。距离大不等于质量更好，非相邻距离也不等于各步距离相加。

可维护性指标：CCN 看控制流复杂度，FFC 看扇入扇出，CBO 看对象耦合，RFC 看响应涉及的方法集合，TCC/LCC 看紧密或间接关联的内聚程度。比较时要保持定义、粒度与测量条件一致。

自编例：某单项指标从 2 变为 4，归一化距离为 |2−4|/(2+4)=1/3；若它是缺陷数，增加通常不好，若是有效覆盖量则需另作判断。不能把距离直接称为收益率。

## 补强：分层实现、SOA 与集成

表现层负责交互；业务逻辑层承载规则与流程；数据访问层封装读写；数据层负责持久化。工作流表达活动、路由、状态和参与者，业务实体表达领域状态及规则。XML 是结构化数据表示，XML Schema 描述结构和类型约束，不能把 XML 文档本身当数据库或执行引擎。

SOA 设计关注契约、松耦合、抽象、复用、自治、无状态和可发现性。实施从业务流程分析和服务识别开始，明确粒度与边界，设计接口、消息、安全和治理，再组装流程、验证并运营。服务注册表支持查找；ESB 提供路由、转换与集成；二者不能互换概念。

企业应用集成可按表示、数据、应用接口和过程等层次分析；数据联邦提供统一查询视图，复制物化副本，接口集成通过约定 API 交换。集成时必须处理语义、格式、时间和事务边界，不能只连通网络。

云上自动化运维可按基础设施即代码、制品、流水线、配置密钥、监测、伸缩、恢复和成本管理组织。度量交付时间、变更失败率、恢复时间及单位业务成本；“自动化”不是删除验证和回滚措施。

## 补强：架构知识管理与 SOA 发展

架构知识不仅包含设计结果，也包含决策及其理由：记录问题、备选、约束、选择、后果和验证，供后续维护人员检索复用。只有结构图而没有决策依据，人员变更后容易丢失上下文。修改管理可建立隔离区域，明确修改规则、影响边界与副作用，再做变更和回归验证；隔离不代表绝对没有外部影响。

按教材对 SOA 发展史的归纳，萌芽阶段以 XML 数据交换为基础，标准化阶段形成 SOAP、WSDL、UDDI 等协议规范，成熟应用阶段进一步出现 SCA、SDO、WS-Policy 等组件、数据及策略规范。这里是教材历史脉络，不是当前产品选型结论；SOA 思想也不能被限定为必须部署 ESB。

## 补强：数据层融合设计

教学归纳：对象映射为关系表时，需要处理身份、关联、多重性和继承：对象引用常通过键关联实现，集合可能需要关联表，继承有多种表映射策略。XML 的层次和重复元素可以映射成表与关联，也可按访问需求保留文档；必须同步考虑 Schema 约束、查询路径和更新事务。不能把对象类或 XML 元素机械地各变成一张表，再假定性能与完整性自然成立。

## 教材案例提要：分层与云原生

以下是教材案例的学习提要，不是对案例中厂商效果或现行产品能力的独立认证。复习抓“问题—方案—取舍”，完整设计与原图回查原节。

| 教材案例 | 核心问题与方案 | 应用辨析 |
|---|---|---|
| PetShop | 数据访问与业务逻辑混杂会放大数据库变化的影响；以清晰分层分离职责 | 增加间接层有成本，不能说分层必然提高性能 |
| 电子小票 | 感知侧采集打印数据，网络层传输处理，应用侧提供小票与数据服务 | 物联网层次与软件内部逻辑分层不是同一维度 |
| 旅行公司 | 技术平台收敛与资源峰谷变化；统一云平台、资源池与弹性 | 运行时对容器配额的识别和隔离也需验证 |
| 汽车公司 | 稳态业务与敏态业务并存；容器平台、混合云、微服务治理与 DevOps | 部署位置按业务管控需求确定，不是全量搬迁 |
| 快递公司 | 旧系统交付慢、数据库职责过重；拆分交易与分析、容器化并按业务域拆服务 | 数据迁移和一致性要与应用改造共同设计 |
| 电商大促 | 高峰容量、第三方慢调用与排障困难；压测、追踪、限流降级和弹性 | 扩容不能修复所有慢 SQL 或依赖故障 |
| 体育用品中台 | 多渠道系统与数据割裂；共享商品、订单、库存等通用能力 | 中台要有业务边界与数据治理，不能只建共享数据库 |

自测：把业务直接写进数据访问层为何影响维护？答案：变化会跨职责传播，数据库或业务规则变化都可能迫使修改同一模块。云原生案例不能只答容器，应同时分析数据、交付、弹性与故障处理。
