# 分布式系统与缓存及大数据

本篇为 AI 辅助整理的非官方学习手册。概念采用教材归纳与明确标出的工程补充；口诀、例题、答案及作答模板均为教学归纳，不是官方答案或真实项目事实。优先级是学习安排，样本考频不代表未来命题概率。

## 五分钟速记

- CAP 的 C 指线性一致性，A 指非故障节点请求得到响应；发生网络分区时不能同时保证这两项，不是任意时刻“随便三选二”。
- 缓存穿透是反复请求不存在的数据；击穿是热点键失效；雪崩是大量键失效或缓存整体故障。
- 熔断防止故障持续扩散；限流控制进入速率或并发；降级减少非核心能力；隔离限制相互影响。
- 消息至少一次可能重复，至多一次可能丢失；业务幂等、事务边界及补偿需一起设计。
- Lambda 维护批、流两条处理链；Kappa 以流处理和可重放日志为核心。

## 1 一致性与分布式事务

CAP 讨论特定网络模型下的保证，分区容忍涉及节点间消息可能无法送达。一致性指读写像作用于单份实时有序的数据，可用性不能简单等同于日常 SLA 百分比。分区期间若拒绝部分请求以保持一致，牺牲相应可用性；若各分区继续独立处理，可能需要之后解决状态分歧。[Gilbert 与 Lynch 的 CAP 论文](https://www.cs.princeton.edu/courses/archive/spr22/cos418/papers/cap.pdf)

BASE 是基本可用、软状态、最终一致性的设计思想；最终一致性需要在更新停止等条件下通过机制使副本收敛，不是“随便等一会儿就一致”。

| 方案 | 核心做法 | 主要代价 |
|---|---|---|
| 2PC | 准备后统一提交或中止 | 协调与锁持有成本；部分故障可能阻塞 |
| TCC | Try 预留、Confirm 确认、Cancel 取消 | 业务侵入，处理空回滚、重复调用及悬挂 |
| Saga | 多个本地事务及业务补偿 | 补偿不一定精确逆转所有外部影响 |
| 本地消息表／Outbox | 业务数据和待发送事件写入同一本地事务，再投递 | 投递仍可能重复，需要幂等与清理 |

上表为工程补充。选型先明确跨哪些资源、允许怎样的中间状态、失败后怎样恢复；不能只写“用分布式事务保证一致”。

复制把相同数据放到多个节点，分片把不同数据分配到不同节点。分片增加容量，但跨片事务、连接、热点和扩容迁移都需设计。

## 2 缓存设计与失效

Cache Aside 的常见读路径：查缓存 → 未命中则查数据库 → 回填缓存。写路径常先更新数据库再使缓存失效，但并发与投递失败仍可能造成不一致，需要重试、版本或补偿机制；这不是严格一致性的通用证明。

| 问题 | 现象 | 可选策略与条件 |
|---|---|---|
| 穿透 | 不存在的数据绕过缓存反复查库 | 参数校验、短时空值缓存、布隆过滤器；注意误判和新增数据维护 |
| 击穿 | 热点键失效，大量请求同时回源 | 单次重建互斥、预热、逻辑过期；权衡等待和旧数据 |
| 雪崩 | 大量缓存同时失效或缓存不可用 | 过期时间分散、多级缓存、高可用、限流降级 |
| 热点 | 少数键或分片承受极高流量 | 热点识别、本地缓存或适当复制；注意一致性与失效传播 |

互斥重建：未命中后竞争重建资格，成功者再次检查缓存、读取数据库并更新，失败者有限等待或降级。锁需有租约与所有者校验，避免持有者故障或误删别人的锁。

逻辑过期：数据带逻辑失效时间，过期时返回允许使用的旧值，同时由一个执行者异步重建。适合允许短时陈旧的查询，不适合直接作为严格扣款或库存真相。

## 3 Redis 的复制与持久化

RDB 保存某个时点的快照，适于紧凑备份和恢复，但故障可能丢失快照后的更新；AOF 记录写入操作，刷盘策略影响丢失窗口与 I/O 成本，日志重写用于控制体积。快照与日志均有资源开销，不能把异步后台工作解释为“对请求零影响”。[Redis 持久化文档](https://redis.io/docs/latest/management/persistence/)

首次或不能部分重同步时，主库提供基准数据并衔接期间增量；副本继续接收后续更新。部分重同步依赖复制历史和偏移等条件，不能认为每次断线都必须全量复制。复制通常存在延迟，主从复制本身不保证已确认写入永不丢失。[Redis 复制文档](https://redis.io/docs/latest/manual/replication/)

缓存、持久化、复制、备份是不同职责；不要把内存缓存直接当作所有业务数据的唯一安全存储。

## 4 消息与事件驱动

消息系统需要回答：何时算发送成功，何时确认消费，失败能否重试，重复如何识别，顺序保证到什么范围，积压如何处理。

| 机制 | 作用 |
|---|---|
| 发布确认与持久化 | 降低发送或节点故障导致的数据丢失风险 |
| 消费确认 | 在合适的业务完成时点确认，而非一收到就确认 |
| 幂等键／唯一约束 | 重试和重复投递不重复改变业务结果 |
| 重试与死信 | 有界重试，无法处理的消息进入受控处置 |
| 分区内有序 | 限定同一业务键的处理顺序，代价是并行度约束 |
| 背压与容量限制 | 限制生产速度或拒绝超负荷，避免无限积压 |

“恰好一次”必须说明覆盖的边界；消息平台内部语义不自动覆盖外部数据库、邮件或支付等副作用。

自编案例：任务已入库但发送通知失败，可将任务与待发送事件在本地事务里记录，投递进程重试，消费者按事件标识去重。不能假定“先写库再发消息”天然原子。

## 5 负载均衡与稳定性治理

| 策略 | 适合线索 | 局限 |
|---|---|---|
| 轮询／加权轮询 | 实例能力相同或权重可预估 | 不直接感知实时忙闲 |
| 最少连接 | 连接负载有代表性 | 连接数不一定等同于计算负载 |
| 响应时间／资源指标动态调度 | 有可靠遥测 | 指标滞后与采集开销 |
| 一致性哈希 | 希望节点变化时减少重映射 | 仍可能热点，虚拟节点不能消除业务热点 |

四层分发依据传输层信息，七层可按 URL、头部等应用信息路由。状态外置或会话粘滞解决的问题不同，后者仍会受实例故障影响。

断路器：关闭时正常调用，打开时快速拒绝，半开时试探恢复。超时必须有预算；重试要限制次数、退避并考虑幂等，避免故障时流量放大。

令牌桶按一定速率补充令牌且允许桶容量范围内突发；漏桶常用于平滑输出。限流与扩容相配合，核心数据库能力仍是边界。

## 6 大数据与数据治理

| 架构 | 组成与处理 | 取舍 |
|---|---|---|
| Lambda | 批处理层、加速层、服务层 | 批量重算与低延迟并行，维护两套逻辑有成本 |
| Kappa | 可重放事件日志、流处理、结果服务 | 一套处理逻辑，历史重放成本及保留范围需评估 |

Lambda 不是云厂商某个同名函数产品。Kappa 不代表永远不处理历史数据；可以重放日志重算，但需要足够历史与计算能力。

工程补充：批处理面向有界数据，流处理面向持续事件；事件时间是事情发生时间，处理时间是系统处理时间。乱序、迟到事件需配合窗口、水位线和补算策略；水位线不是绝对保证之后没有迟到数据。

数据仓库面向主题、集成、相对稳定并反映历史变化；OLTP 重事务处理，OLAP 重分析查询。数据治理包括标准、质量、元数据、主数据、血缘、安全与生命周期；不是只安装一个数据平台。

## 自编自测与参考答案

1. 同一不存在的编号反复查库是什么？——穿透；空值缓存或过滤结构须考虑更新与误判。
2. 热点缓存过期时返回旧值的方案牺牲什么？——数据新鲜度，换取响应与可用性。
3. 消费者完成业务后确认丢失，重发会怎样？——可能重复消费，需要幂等，不能只依赖确认机制。
4. 断路器半开时放全部请求吗？——通常有限试探，依据结果恢复或重新打开。
5. Kappa 能处理历史重算吗？——可通过重放日志，但受保留范围与资源约束。
6. 网络分区时每个节点都接受写入就有线性一致性吗？——不能直接保证，需要额外协调或冲突处理，CAP 限制仍存在。
7. 样本练习：2025 上案例四、论文一和三；2025 下案例三、论文四；综合上 8、39，下 58。

完成标准：能够写出成功路径、故障路径、重试与幂等、数据一致性边界及监控验证。

## 补强：缓存并发与分布式锁

Cache-Aside 的典型读路径：先读缓存，未命中时读数据库并填缓存。典型更新路径：提交数据库更新后删除缓存。仍可能出现旧查询先读到旧值、随后在删除之后回填旧值的竞态；删除也可能失败。应按业务选择版本检查、同一键串行处理、可靠失效通知与补偿、TTL 及定期核对。延迟双删依赖时间假设，不是强一致性的证明。

分布式锁先定义保护对象与失效模型。数据库唯一约束或行锁易结合事务，但会占用数据库资源；缓存锁访问快，但租约、主从切换和客户端暂停会影响互斥保证。获取锁需把“不存在才写”和过期时间原子设置；释放时原子比较持有者标识再删除，避免误删别人的新锁。超时后旧持有者仍可能继续写，关键资源还应验证单调 fencing token 或使用具备所需一致性语义的协调机制。参考：[Redis 分布式锁文档](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)。

复制、Sentinel 和 Cluster 分别侧重数据副本、监测及主节点故障转移、分片与集群管理，不能简单说三者都天然强一致。ZSET 以成员和分数组织有序集合；识别写成员及分数、按范围读、取成员分数的任务，再回查对应版本命令，避免把列表和有序集合混用。

## 补强：多源异构数据集成

| 方式 | 数据在哪里处理 | 代价与适用边界 |
|---|---|---|
| ETL | 抽取、转换后装载 | 入库前统一质量，但链路和批次可能增加时延 |
| ELT | 先装载后在目标平台转换 | 利用目标算力，同时增加原始数据治理要求 |
| CDC | 捕获源端变更并增量同步 | 处理全量与增量衔接、顺序、重复及模式演变 |
| 数据联邦 | 查询时访问多个源并组合 | 减少复制，但受源端可用性和跨源查询成本影响 |
| API／消息集成 | 按契约交换业务对象或事件 | 要管理接口版本、幂等和事务边界 |

流程：盘点数据源与语义→统一标识、单位、时间和编码→抽取或订阅→清洗校验与实体消歧→存储计算→发布服务→维护血缘、权限、质量与对账。相同字段名不保证同义，简单拼表不能解决主数据冲突。

HDFS 面向分布式文件存储；HBase 面向大规模宽列数据访问；文档数据库适合结构灵活的文档对象；搜索引擎通过倒排索引等结构支撑检索；关系数据库适合具有明确关系和事务约束的数据。冷热分层按访问频率、时延、容量、成本与恢复要求选介质，不能只按数据年龄判断冷热。

自编练习：订单 CDC 消息重复到达，如何避免重复入账？参考答案：用稳定事件或业务标识去重，并使消费状态与入账副作用处于可保证一致的事务或处理机制中；只有消息确认不够。原始日志保留可重放能力，重放时也要避免重复副作用。

## 教材案例提要：大数据

| 教材案例 | 需求与架构选择 | 复习重点 |
|---|---|---|
| 奥运转播分析 | 当日概览需要增量实时统计，赛事回顾需要历史分析；使用 Lambda 分工 | 批处理、加速与查询服务各自负责什么 |
| 广告平台 | 不同时间和业务维度的指标结合实时与离线数据，逐版演进 Lambda | 分区复制、原始数据保留与重算能力 |
| 证券日志分析 | 集中检索、可视分析和监控；用 Kappa 处理实时日志 | 如何管理日志、消费位置、检索与故障定位 |
| 电商智能决策 | 实时事件驱动参数计算与迭代，使用 Kappa 流式处理 | 数据、计算状态、参数发布和恢复之间的关系 |

以上为教材案例提要，不认证厂商宣传指标。自测：广告平台的统计口径改动后为什么保留原始数据有价值？答案：可用修正后的逻辑重放重算，并与历史结果核对；仍需考虑保留成本与访问控制。
