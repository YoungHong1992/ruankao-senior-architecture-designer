# 架构基础与质量属性及架构评估

## 1 学习范围与优先理由

本单元覆盖架构概念、主要架构风格、质量属性及场景、4＋1 视图、基础架构评估和答题方法。它们同时支撑综合知识辨认、案例分析与论文论证，因此作为首个学习单元。

这是阶段性的核心知识范围，不是教材第 7、8 章的完整替代。基于架构的软件开发方法、架构复用、特定领域架构与评估详细步骤接续见[第 04 篇](04-架构设计方法与分层及云原生.md)；具体计算还需结合原题训练。

本篇为 AI 辅助整理的非官方学习手册。第 2～4、6～8 节以教材知识归纳为主；第 5 节为关联概念与工程补充；口诀、答题模板及练习均为教学归纳。所有示例均为自编教学假设，不是历年真题、官方答案或真实项目实施记录。概念出处见末尾教材回查入口。

学习主线：**需求 → 质量目标 → 架构设计 → 收益与代价 → 验证。**

例如：高峰期提交缓慢 → 缩短提交响应时间 → 将允许延迟的分析异步处理 → 减少等待但增加消息处理复杂度 → 用负载测试验证。

## 2 架构基本概念

| 概念 | 核心含义 | 教学示例 |
|---|---|---|
| 架构 | 系统的一个或多个结构，包括构件、外部可见属性及相互关系 | 采集、分析、存储如何组织和协作 |
| 构件 | 执行计算或保存数据的组成部分 | 分析服务、数据库 |
| 连接件／连接子 | 构件之间的交互机制 | 过程调用、消息传递、数据流 |
| 外部可见属性 | 其他构件使用它时需要了解的性质 | 接口、数据格式、行为约束 |
| 架构风格 | 一类系统的组织方式，规定构件与连接件类型及组合约束 | 分层、管道—过滤器、事件系统 |

架构关注系统整体组织与关键决策。函数内局部变量命名通常属于实现细节。

**教学辨析：风格与策略。** 分层描述系统如何组织；缓存是为减少重复访问或计算而采用的设计策略。采用分层风格的系统，也可以同时使用缓存、冗余、访问控制等策略。

**记忆抓手：架构看组成和关系，风格看组织模式，策略看质量目标。**

## 3 质量属性与题干识别

“能够采集信息”是功能要求；“高峰期仍在两秒内完成提交”涉及性能要求。判断时看指标在衡量什么，不只看技术名或是否出现数字。

| 属性 | 判断抓手 | 自编题干示例 |
|---|---|---|
| 性能 | 响应时间、吞吐量、处理能力 | 95% 的查询在两秒内返回 |
| 可用性 | 服务可用时间比例、故障恢复 | 节点故障后三十秒恢复服务 |
| 可靠性 | 规定条件和时间内持续无故障完成规定功能 | 连续运行期间正确完成规定任务 |
| 安全性 | 授权、保密、防篡改、追溯 | 非授权用户不能查看数据 |
| 可修改性 | 变更成本、工期、影响范围 | 修改规则只涉及一个模块 |
| 可测试性 | 控制输入、观察输出、发现缺陷 | 能模拟外部依赖并验证结果 |
| 易用性 | 学习与操作难度 | 新用户能快速完成操作 |
| 可伸缩性 | 负载增长后的服务能力 | 增加实例以承受更多请求 |
| 可扩展性 | 增加或替换功能 | 新增一种业务分析功能 |
| 互操作性 | 系统间交换数据和调用服务 | 与外部系统交换任务信息 |
| 可移植性 | 更换运行环境的难易程度 | 迁移到另一操作系统 |

### 必须区分的概念

- **可靠性与可用性：**前者强调持续无故障运行，后者强调可提供服务的时间比例。发生故障后迅速恢复，系统仍可能具有较高可用性。
- **可扩展性与可伸缩性：**增加业务功能与应对负载增长。两者可能关联，但关注点不同。
- **性能与可用性：**“正常查询两秒返回”主要涉及性能；“故障后三十秒恢复”主要涉及可用性。
- **功能与质量要求：**“能够查询”说明做什么；“在给定负载下多快返回”说明做得怎样。

质量属性的分类会随质量模型而变化。遇到题目明确指定模型时，按指定模型作答，不能机械套用本表。

## 4 质量属性场景

六要素：**刺激源、刺激、环境、制品、响应、响应度量。**

理解方法：谁，在什么条件下，对系统哪部分造成什么事件；系统如何处理，怎样衡量结果。

自编示例：高峰期，采集人员向采集服务提交记录，服务完成校验和保存，95% 的请求在两秒内返回。

| 要素 | 示例中的内容 |
|---|---|
| 刺激源 | 采集人员 |
| 刺激 | 提交记录 |
| 环境 | 高峰期 |
| 制品 | 采集服务 |
| 响应 | 校验、保存并返回 |
| 响应度量 | 95% 的请求在两秒内返回 |

制品是受影响的系统或系统部分。响应是系统做什么；响应度量是如何判定是否达标。“快速响应”“具有较高可用性”不足以形成精确的度量。

教材在架构评估概述中也使用“刺激、环境、响应”的简化场景描述；题目要求六要素时应完整列出六项。

## 5 关联概念与工程补充

本节将架构与质量属性联系到工程实践，属于教学补充，不是教材策略分类的逐字转录。

### 质量目标与策略

| 目标 | 常用策略示例 | 需要解释的作用机制 |
|---|---|---|
| 性能 | 缓存、并发、减少计算、资源调度 | 减少重复工作、等待或资源争用 |
| 可用性 | 故障检测、冗余、故障切换、恢复 | 发现故障并缩短服务中断 |
| 安全性 | 认证、授权、加密、审计 | 确认身份、限制操作、保护数据、追溯行为 |
| 可修改性 | 信息隐藏、职责分离、稳定接口 | 限制变更影响范围 |
| 可测试性 | 可控输入、可观察输出、测试接口 | 便于构造条件和验证结果 |

策略与质量属性不是固定的一对一关系。冗余可以改善可用性，也会增加资源成本和状态同步复杂度。

### 高内聚、低耦合、信息隐藏

- **高内聚：**一个模块内部的职责紧密相关。
- **低耦合：**模块之间的依赖尽量少而清晰，不代表模块完全没有交互。
- **信息隐藏：**将容易变化的实现细节封装在模块内部，通过稳定接口提供能力。

这些设计有助于减少修改的连锁影响；仍需根据具体依赖关系判断效果。

### 异步处理与幂等性

消息队列可以缓冲突发流量、解耦耗时处理，但不会自动增加消费者的处理能力，也不保证缩短端到端处理时间。选择异步前，要确认业务是否允许结果延迟产生。

**幂等性：**同一操作执行一次或多次，对业务状态产生相同效果。例如，同一创建任务请求重复到达时，不重复创建任务。可结合唯一业务标识与去重机制实现；具体方案取决于业务及并发条件。

## 6 架构风格速查

### 教材分类

| 大类 | 典型风格 |
|---|---|
| 数据流 | 批处理、管道—过滤器 |
| 调用／返回 | 主程序—子程序、面向对象、层次型、客户端／服务器 |
| 以数据为中心 | 仓库、黑板 |
| 虚拟机 | 解释器、规则系统 |
| 独立构件 | 进程通信、事件系统 |

### 结构特征与易混点

| 风格 | 核心结构特征 | 辨认提示 |
|---|---|---|
| 批处理 | 完整批次在处理步骤间传递 | 后一步等待前一步完成整批 |
| 管道—过滤器 | 过滤器转换数据，管道传递数据流 | 可以增量处理，不必等待整批完成 |
| 主程序—子程序 | 通过调用和返回组织控制 | 强调调用层次 |
| 面向对象 | 封装数据及操作，对象相互协作 | 构件是对象 |
| 层次型 | 各层提供不同抽象层次的服务 | 逻辑分层不等于部署在不同机器 |
| 客户端／服务器 | 客户请求服务，服务器提供服务 | 区分两层与三层的职责分配 |
| 仓库 | 独立构件围绕中央共享数据协作 | 使用数据库不等于整体采用仓库风格 |
| 黑板 | 多个知识源围绕共享问题状态协同求解 | 黑板、知识源、控制机制 |
| 解释器 | 解释引擎执行某种表示或语言 | 不等同于部署虚拟机 |
| 规则系统 | 规则集与解释执行机制组织处理 | 规则与执行机制分离 |
| 进程通信 | 独立进程通过消息等机制交互 | 可同步，也可异步 |
| 事件系统 | 发布事件，由注册或订阅者响应 | 发布者无需知道具体订阅者 |

分层有利于职责分离和局部替换，也可能增加层间调用开销。事件系统有利于降低直接依赖，但需要处理执行顺序、结果追踪与错误处理问题。

工程辨析：一个系统可以组合多种风格；事件驱动不必然异步；仅凭某个技术产品名无法确定整个系统的架构风格。

## 7 4＋1 架构视图

不同视图描述同一个系统的不同侧面，体现关注点分离。下表为教材所列视图的教学解释。

| 视图 | 主要回答 |
|---|---|
| 逻辑视图 | 系统有哪些主要功能抽象、对象及关系 |
| 开发视图 | 代码如何组织成模块、包、子系统 |
| 进程视图 | 运行时有哪些进程及并发、通信、同步关系 |
| 物理视图 | 软件如何映射和部署到硬件节点 |
| 场景／用例（＋1） | 如何通过具体使用场景串联和验证各视图 |

记忆口诀：**逻辑看功能结构，开发看代码组织，进程看运行协作，物理看部署，场景贯穿验证。**

开发视图与进程视图的区别是“代码如何组织”与“运行时如何协作”；进程视图与物理视图的区别是“运行实体的关系”与“部署到哪些节点”。

## 8 架构评估

### 方法辨认

| 方法 | 核心关注 |
|---|---|
| SAAM：软件架构分析方法 | 基于场景分析，主要关注可修改性 |
| ATAM：架构权衡分析法 | 多个质量属性及其相互权衡 |
| CBAM：成本效益分析法 | 架构策略的成本、收益与投资回报 |

记忆口诀：**SAAM 看修改，ATAM 看权衡，CBAM 看经济性。** 这是辨认抓手，不是对方法适用范围的完整定义。

### 敏感点与权衡点

| 概念 | 判断依据 |
|---|---|
| 敏感点 | 某个架构特性显著影响某项质量属性 |
| 权衡点 | 某个架构特性同时影响多个质量属性，是多个质量属性的敏感点 |

自编示例：加密方案显著影响数据保护能力，同时影响计算开销和响应时间，可能构成安全性与性能的权衡点。

权衡点不是泛指“这个决策很重要”，必须指出它影响的质量属性。典型表现是一项改善而另一项付出代价，但定义不限于这种情况。

### ATAM 效用树

结构：**树根 → 质量属性 → 属性分类 → 具体质量属性场景。**

叶子应落到具体场景。教材中的优先级对按“重要度、实现难度”理解：

- （H，H）：重要且难实现。
- （H，L）：重要且容易实现。

第二个 H 不代表实现效果好。具体评估仍需分析场景、架构方案及其风险，不能只看标签。

## 9 案例与论文表达

以下模板和示范均为教学归纳，不是官方评分标准。

### 案例模板

针对【具体问题】，在【适用条件】下采用【策略】，通过【作用机制】改善【质量属性】；同时处理【代价或风险】，并通过【测试或指标】验证。

自编案例：采集系统在高峰期提交缓慢；分析服务故障会阻塞采集；新增分析功能需要修改采集代码。

| 现象 | 主要关注属性 | 可考虑的改进 |
|---|---|---|
| 高峰提交缓慢 | 性能 | 分析瓶颈，缩短提交关键路径 |
| 分析故障阻塞采集 | 可用性 | 故障隔离、异步解耦 |
| 新增分析必须修改采集代码 | 可修改性 | 稳定事件接口、订阅机制 |

教学参考答案：在业务允许分析结果延迟产生的前提下，将采集提交与后台分析解耦。采集服务完成必要校验和可靠保存后，通过消息机制通知分析服务，减少提交链路中的等待，并降低分析故障对采集业务的影响。新增分析模块通过订阅约定事件接入，减少对采集代码的修改。同时需要处理可靠投递、重复消费和消息积压，并通过负载及故障测试验证效果。

只写产品名或“使用消息队列提高性能”不足以说明设计合理性。需要把题目现象、策略、机制和约束连起来，具体实现还需处理保存数据与发送消息的一致性等问题。

### 论文论证模板

**实际问题 → 设计选择 → 实施过程 → 效果证据 → 局限与改进。**

每个技术论点都应说明为什么需要、如何使用、解决什么、付出什么代价、有什么效果证据。项目职责、实施过程和效果使用真实经历，不能把本篇假设或示例数字当成项目成果。本模板只是论证方法，不能替代论文题目要求。

## 10 自编自测与教学参考答案

先遮住答案，写出概念及判断理由，再核对。

### 自测

1. 描述软件架构时，三个核心要点是什么？
2. 将“高峰期用户提交记录，采集服务校验并保存，95% 的请求两秒内返回”拆成场景六要素。
3. “查询两秒内返回”和“故障后三十秒恢复”主要分别涉及什么质量属性？
4. 新增一种采集业务与增加实例承受更多请求，分别侧重什么属性？
5. 完整批次逐步传递与增量数据流逐步处理，分别对应什么风格？
6. 黑板系统由哪些主要部分组成？共享一个数据库是否足以判定为黑板风格？
7. 描述代码包组织和服务部署节点，分别使用哪两个视图？
8. 比较修改成本、多属性权衡、投资回报，分别优先联想到哪种评估方法？
9. 加密方案显著影响安全性与性能，是哪类关键点？效用树（H，L）表示什么？
10. 为什么不能直接断言“加消息队列就提高性能”？回答至少两个条件或代价。
11. 新分析模块必须修改采集代码，主要暴露什么问题？写出改进机制。
12. 同一创建任务请求重复到达却不重复创建任务，体现什么性质？

### 参考答案

1. 构件、构件的外部可见属性、构件之间的相互关系。
2. 刺激源：用户；刺激：提交记录；环境：高峰期；制品：采集服务；响应：校验、保存并返回；响应度量：95% 的请求两秒内返回。
3. 性能、可用性。判断依据分别是正常响应时间与故障恢复时间。
4. 可扩展性、可伸缩性，分别关注功能增长与负载增长。
5. 批处理、管道—过滤器。
6. 黑板、知识源、控制机制。不能只凭共享数据库判断，还需看是否围绕问题状态协同求解。
7. 开发视图、物理视图。
8. SAAM、ATAM、CBAM；实际方法的范围不止这些记忆标签。
9. 权衡点；（H，L）表示重要度高、实现难度低。
10. 业务需要允许结果延迟；消费者能力仍是约束；可能出现积压、重复处理或投递失败；不保证缩短端到端耗时。任举两点并解释即可。
11. 主要涉及可修改性。可通过稳定事件接口让新模块订阅，减少直接依赖，但仍需管理事件契约的变化。
12. 幂等性：重复执行对业务状态产生与执行一次相同的效果。

## 11 快速复习与完成标准

两分钟回忆：

1. 架构三要点：构件、外部属性、关系。
2. 场景六要素：刺激源、刺激、环境、制品、响应、响应度量。
3. 可靠性看持续无故障，可用性看可服务时间比例。
4. 扩展看功能增长，伸缩看负载增长。
5. 批处理整批传递，管道连接数据流处理阶段。
6. 黑板包括黑板、知识源、控制机制。
7. 视图区分逻辑、开发、进程、物理，场景贯穿验证。
8. SAAM 看修改，ATAM 看权衡，CBAM 看经济性。
9. 策略答案写出条件、机制、代价和验证。
10. 示例用于理解，论文项目事实必须真实。

阶段完成标准：能辨认陌生题干中的属性和风格；能解释策略的收益及代价；能按模板写出完整案例答案。完成背诵不等于完成应用训练，仍需通过真题练习验证。

## 补强：架构师角色与能力

教材归纳：架构师可以是个人或团队角色，负责关键结构、质量需求、核心技术与接口决策，并通过架构视图和文档使决策可沟通、可实施、可评价。项目经理侧重资源、进度和成本；架构师侧重技术方向与技术风险，两者需要协作，不能互相替代。

能力包括业务领域知识、技术知识、设计和编程、沟通、决策与团队领导。教材把成长过程概括为工程师、高级工程师、技术专家及不同层次的架构师；这是能力发展描述，不是考试报名资格或统一职业晋升规则。训练应从参与实现、理解整体设计逐步扩展到跨系统决策，并复盘决策结果。

自编自测：只决定使用哪个框架是否完成架构师任务？答案：没有，还需解释业务和质量约束、组织结构接口、分析风险与取舍，并验证实现结果。
