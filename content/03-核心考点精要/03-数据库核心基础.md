# 数据库核心基础

本篇为 AI 辅助整理的非官方学习手册。概念采用教材归纳与明确标出的工程补充；口诀、例题、答案及作答模板均为教学归纳，不是官方答案或真实项目事实。优先级是学习安排，样本考频不代表未来命题概率。

## 学习范围与优先级

优先级 P0。2023 年起仓库五场考试的主主题统计：综合知识 27 题、案例 0 道大题、论文 2 题。每题只归一个主主题；组内粒度不同，计数不代表单考点概率或预测分值。具体题号与分年结果见[样本记录](../../verification/核心考点精要-考频样本.md)，覆盖边界见[覆盖表](11-大纲与教材考点覆盖表.md)。

## 五分钟速记

- 表是关系的常用表示，行对应元组，列对应属性；关系代数采用集合语义，SQL 默认可保留重复行。
- 候选键是最小超键；主键是选中的候选键；主属性属于任意候选键，不只主键。
- 外模式面向用户，模式描述全局逻辑，内模式描述物理存储。
- 选择筛行，投影选列，连接拼关系，除法回答“满足所有要求”。
- 事务 ACID：原子性、一致性、隔离性、持久性。两段锁与两阶段提交不同。
- 规范化减少异常；索引改善特定访问路径，同时增加存储和写入维护代价。

## 1 三级模式、键与完整性

| 概念 | 含义 |
|---|---|
| 外模式 | 用户或应用看到的局部逻辑视图，可有多个 |
| 模式 | 数据库全局逻辑结构 |
| 内模式 | 文件组织、存储路径等物理结构 |
| 外模式／模式映像 | 支持逻辑数据独立性 |
| 模式／内模式映像 | 支持物理数据独立性 |
| 超键 | 可以唯一识别一行的属性集 |
| 候选键 | 无法再去掉属性的超键，强调最小性 |
| 主键 | 选作主要标识的候选键 |
| 外键 | 引用本表或另一表的键值以约束关联 |

工程辨析：外键也可能是本表主键的一部分，甚至与本表主键相同；不要把“外键不是本表的键”当作一般定义。

实体完整性要求主键唯一且非空；参照完整性约束引用值；用户定义完整性表达具体业务规则。组合主键要求整个组合唯一，不要求每个组成列分别唯一。

设计阶段：需求分析 → 概念设计（E-R 模型）→ 逻辑设计（关系模式）→ 物理设计（索引、组织与存储）→ 实施 → 运行维护。

E-R 转换：实体转表；1:N 联系常在 N 端放外键；M:N 联系通常单独建关联表，保存双方标识和联系属性。具体主键还取决于时间、重复发生等业务约束。

## 2 函数依赖与候选键

$X\to Y$ 表示在合法关系中，相同 X 值必须对应相同 Y 值，不是某次样本数据偶然没有重复。

求 $X^+$：从 X 出发，反复使用依赖把能推出的属性加入，直到不再变化。若覆盖全部属性，X 是超键；再逐个尝试删属性，验证最小性。

自编例：R(A,B,C,D)，依赖 A→B、B→C、A→D。

1. A 的闭包从 A 得到 B、D，再由 B 得到 C，故 A⁺=ABCD。
2. A 是单属性超键且最小，因此是候选键。
3. B⁺=BC，不覆盖全部，B 不是候选键。

只在依赖左侧出现、从不在右侧出现的属性必须包含在候选键中；两侧都没出现的属性同样需要。随后仍要用闭包验证，不能只凭口诀结束。

Armstrong 公理：自反、增广、传递。最小依赖集常按“右部拆单属性—删左部冗余属性—删冗余依赖”处理，每次删除后都用闭包验证。

## 3 范式与分解

| 范式 | 判断核心 |
|---|---|
| 1NF | 按当前关系模型要求，属性取原子值 |
| 2NF | 1NF；非主属性完全依赖每个候选键，不存在对候选键的部分依赖 |
| 3NF | 对每个非平凡依赖 X→A，X 是超键，或 A 是主属性 |
| BCNF | 对每个非平凡依赖 X→Y，X 都是超键 |
| 4NF | 非平凡多值依赖的决定因素必须是超键，关注独立多值事实带来的冗余 |

非平凡 X→Y 指 Y 不包含于 X。3NF 的形式判断能处理多个候选键，比“消除传递依赖”的口诀更可靠；BCNF 比 3NF 严格。

自编例：选课表（学号、课程号、学生名、课程名、成绩），候选键为（学号、课程号）。学生名只依赖学号，课程名只依赖课程号，是部分依赖，不满足 2NF。拆成学生、课程、选课三表可减少重复与修改异常。

进一步：学生表（学号、系号、系名），学号→系号→系名，会产生非主属性的传递依赖；将系信息独立建表。

**无损连接与保持依赖是两个条件。** 无损关注分解后能否正确重建原关系；保持依赖关注能否通过分解后各关系的约束检查原依赖。

二元分解 R→R1、R2 在函数依赖下无损，当且仅当公共属性能函数确定 R1 或 R2，即交集→R1 或交集→R2 在 F⁺ 中成立。BCNF 分解能做到无损，但不保证保持全部依赖；3NF 合成可兼顾无损与依赖保持。

工程补充：适度反规范化可换取特定查询性能，但要说明冗余维护和一致性代价，不是范式越低越快。

## 4 关系代数与 SQL

| 运算 | 作用 |
|---|---|
| 选择 σ | 筛满足条件的行 |
| 投影 π | 取指定属性列；集合语义下去重 |
| 笛卡尔积 × | 所有行组合 |
| 连接 ⋈ | 按条件组合行；自然连接匹配同名属性并合并重复列 |
| 并、交、差 | 同构关系上的集合操作；R−(R−S)=R∩S |
| 除 ÷ | 找到与要求集合中全部元素都有关联的对象 |

工程补充示例：统计每名人员已完成任务数，并保留没有完成任务的人员。

```sql
SELECT p.id, COUNT(t.id) AS completed_count
FROM person AS p
LEFT JOIN task AS t
  ON t.person_id = p.id AND t.status = 'completed'
GROUP BY p.id;
```

把右表状态条件放到 WHERE 中，可能过滤掉补 NULL 的行，从而丢掉没有完成任务的人员。COUNT(*) 数行，COUNT(t.id) 忽略 NULL；空值用 IS NULL 判断，不能写 `= NULL`。

理解顺序：FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY。WHERE 筛行，HAVING 筛分组；这是逻辑理解顺序，不等于数据库实际执行计划。

## 5 事务、锁与隔离

ACID：原子性保证事务整体完成或撤销；一致性关注事务前后满足约束；隔离性控制并发干扰；持久性关注提交结果在故障后的保留。ACID 的一致性与 CAP 的一致性含义不同。

| 并发异常 | 含义 |
|---|---|
| 脏读 | 读到另一事务尚未提交的数据 |
| 不可重复读 | 同一事务重读同一数据，读到其他事务提交的修改 |
| 幻读 | 按相同条件查询，符合条件的行集合因他人提交而改变 |
| 丢失更新 | 并发写入覆盖了另一个更新效果 |

SQL 标准隔离级别的最低要求：读未提交可能脏读；读已提交防脏读；可重复读还防不可重复读；可串行化提供与某种串行执行等价的效果。具体实现可能更强，例如 PostgreSQL 的可重复读还避免幻读；不要把标准允许现象当成所有产品必然行为。[PostgreSQL 隔离说明](https://www.postgresql.org/docs/current/transaction-iso.html)

共享锁 S 通常用于读，多个 S 可兼容；排他锁 X 用于写，与其他事务的 S、X 冲突。MVCC 通过多版本支持并发读写，但不等于完全不用锁。

两段锁 2PL：增长阶段获取锁，收缩阶段释放锁；基本 2PL 能保证冲突可串行化，但仍可能死锁。两阶段提交 2PC：分布式事务的准备与提交／中止协议，不能与 2PL 混淆。

## 6 索引、恢复与数据库选型

工程补充：B+ 树适合有序访问与范围查询；哈希索引主要适合等值查找，不能一般性支持范围排序。索引不是越多越好，它增加空间及 INSERT/UPDATE/DELETE 的维护成本。

复合 B 树索引（a,b,c）常受前导列和谓词形式影响；选择性、回表、排序和优化器都会影响收益，不能只背“有索引一定走索引”。覆盖索引所需列均可由索引取得，可减少表访问。

日志恢复通常区分撤销未完成事务与重做应保留的修改；备份用于恢复，复制用于副本同步，两者不能相互替代。检查点减少恢复时需处理的历史范围，但不是完整备份。

| 模型 | 合适线索 | 代价 |
|---|---|---|
| 关系 | 结构与约束明确、连接和事务重要 | 大规模分布式扩展需要额外设计 |
| 键值 | 按键访问、缓存、会话 | 复杂关联查询能力有限 |
| 文档 | 聚合对象、结构灵活 | 跨文档约束和查询需关注实现 |
| 宽列 | 大规模稀疏数据、特定键范围访问 | 建模依赖访问模式 |
| 图 | 实体关系与多跳遍历 | 分区及跨图遍历成本需评估 |
| 多模型 | 同一系统支持多种数据模型 | 是否降低总体复杂度需验证，不自动优于多库 |

## 自编自测与参考答案

1. R(A,B,C)，A→B、B→C，候选键是什么？——A；A⁺=ABC 且最小。
2. 组合主键 AB，C 只依赖 A，满足 2NF 吗？——若 C 为非主属性则不满足。
3. 所有决定因素都是超键，对应哪个范式条件？——BCNF 的函数依赖条件。
4. 外模式改变物理文件位置吗？——不是，它面向用户局部逻辑视图；物理组织属于内模式。
5. 事务读取另一事务后来回滚的值是什么？——脏读。
6. 2PL 能消除死锁吗？——不能；它与分布式 2PC 也不同。
7. 人员与房屋可能多对多且入住有时间范围，怎么建模？——独立关联记录，包含双方标识及入住／离开时间；主键和约束据业务确定，不能只在人员表放一个房屋字段。
8. 样本练习：2025 上综合 7、32–34、37；2025 下综合 7–8、45、53、72；两场论文的数据库主题。

完成标准：能求闭包与候选键、判断典型范式问题、读简单 SQL，并解释事务异常和数据库选型条件。

## 补强：数据库设计全流程与访问接口

| 阶段 | 主要输入与产物 | 区分线索 |
|---|---|---|
| 需求分析 | 数据项、处理需求、数据字典与约束 | 先了解业务，不急于选索引 |
| 概念设计 | 局部 E-R 模型及合并后的全局模型 | 处理命名、属性和结构冲突 |
| 逻辑设计 | 关系模式、键、完整性、规范化与用户视图 | 将概念模型映射为逻辑模型 |
| 物理设计 | 存储组织、分布、访问路径和索引 | 针对工作负载及具体 DBMS |
| 实施 | DDL、数据转换加载、应用联调和试运行 | 先校验数据质量及约束 |
| 运行维护 | 性能监测、备份恢复、重组与重构 | 变更后验证正确性和性能 |

反规范化是为访问效率引入可控冗余，必须说明更新一致性由谁保证；不要把“冗余越少越快”或“反规范化必然更快”当结论。重组调整物理组织，重构涉及模式等设计变化，具体含义结合题设。

库函数接口通过厂商 API 调用数据库；嵌入式 SQL 把 SQL 写入宿主语言并经预处理；ODBC 提供通用调用接口并通过驱动适配数据库；ORM 建立对象与关系数据映射。JDBC 是 Java 数据库访问接口，JPA 是持久化规范，Hibernate 是实现与框架，MyBatis 侧重 SQL 映射。使用 ORM 仍需理解事务、查询次数、连接池和生成 SQL。

教材归纳的 NoSQL 四层框架为数据持久层、数据分布层、数据逻辑模型层、接口层；四类模型为键值、文档、列族/宽列和图。这里的宽列数据库不能直接等同于分析型关系数据库的列式存储布局。

自编练习：E-R 图合并时两个部门都用“客户”但范围不同，应先处理什么？答案：语义与结构冲突，统一概念后再转关系模式。连接池解决连接复用与资源控制，不自动扩大数据库处理能力。

## 补强：数据库系统与数据模型

教学归纳：DB 是有组织的数据集合，DBMS 是管理数据库的软件，DBS 包括数据库、管理系统、相关应用及运行管理环境。DBMS 提供定义、查询更新、事务并发、完整性、安全与恢复等能力。层次模型以树组织，网状模型允许更一般的记录联系，关系模型以关系及其操作表达；分布式数据库关注跨节点数据组织与访问，并行数据库关注并行执行，二者可能结合。数据仓库侧重面向分析的数据集成，不能与在线事务处理无条件互换。
