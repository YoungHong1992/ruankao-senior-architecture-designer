# 2024年下半年系统架构设计师论文（清洗版）

> **主试题数量：** 4 个论题。
>
> **作答规则：** 论文科目通常从四个论题中任选一个作答，具体以当次试卷为准。

## 试题一：论分布式事务及其解决方案

请围绕“论分布式事务及其解决方案”论题，依次从以下三个方面进行论述。

### 写作要求

1. 概要叙述你参与分析、设计的软件项目，以及你在其中所承担的主要工作。
2. 介绍四种分布式事务解决方案，并作简要说明。
3. 具体阐述你参与的软件项目如何处理分布式事务，过程中遇到了哪些问题，以及如何解决。

### 参考提纲

1. 对应要求 1，先界定真实业务事务跨越哪些服务、数据库或外部系统，说明一致性等级、可接受时延、吞吐量和补偿边界，以及本人承担的事务拆分、选型或故障治理职责。
2. 四种方案可写：① `XA/2PC`，由协调者驱动准备和提交/回滚，隔离和一致性较强，但长时间占锁、可用性和吞吐受影响；② `AT`，代理业务 SQL，在本地事务中保存回滚日志并用全局锁协调，业务侵入小，但依赖支持的关系数据库和 SQL 语义；③ `TCC`，业务显式实现 Try 资源预留、Confirm 确认和 Cancel 释放，性能和资源粒度可控，但侵入大且必须处理幂等、空回滚和悬挂；④ `Saga`，长流程由一串本地事务和补偿事务组成，可编排或事件协同、吞吐高，但通常只有最终一致且隔离弱。
3. 选型应由业务语义决定：短事务且必须强一致可考虑 XA；常规关系库低侵入场景可考虑 AT；核心库存/额度等可预留资源的高并发场景可考虑 TCC；跨组织或长流程可考虑 Saga。消息事务/Outbox 也可作为其他分类中的方案，但不要与上述四项重复计数。
4. 对应要求 3，沿一笔真实交易说明全局标识、各本地事务、状态机、超时/重试、幂等键、补偿顺序、死信和人工兜底。问题应覆盖网络超时导致结果未知、重复消息、部分成功、补偿失败、并发脏读、下游不可用与链路难追踪；用状态持久化、去重、可重入补偿、对账、熔断、告警和演练解决。
5. 效果用事务成功率、P95/P99、锁持有时间、补偿率、补偿恢复时间、积压量和对账差异衡量，不得只写“保证了强一致性”。

## 试题二：论多源异构数据集成方法

请围绕“论多源异构数据集成方法”论题，依次从以下三个方面进行论述。

### 写作要求

1. 概要叙述你参与分析、设计的软件项目，以及你在其中所承担的主要工作。
2. 说明多源异构数据集成有哪些方法。
3. 具体阐述你参与的软件项目如何进行多源异构数据集成，过程中遇到了哪些问题、如何解决，以及处理后的效果。

### 参考提纲

1. 对应要求 1，列出真实数据源类型、模式/编码/协议差异、更新周期、数据量、消费方和安全边界，说明本人负责的数据模型、管道、治理或服务层。
2. 对应要求 2，可用四类方法组织：① ETL/ELT 物化集成，将源数据批量汇入仓库或湖仓；② 复制/CDC 增量集成，维持近实时副本；③ 联邦查询/数据虚拟化，通过统一逻辑视图访问原地数据；④ API、消息和流式事件集成，用契约连接实时应用。语义异构还需模式映射、统一词汇/本体、主数据和实体解析，它们是横跨上述方法的治理能力。
3. 对应要求 3，可按“数据源盘点与元数据 → 统一业务术语和规范模型 → 连接器及全量基线 → CDC/事件增量 → 格式、单位、编码和时区转换 → 清洗、去重、实体匹配 → 质量规则与隔离 → 血缘、权限和数据服务”描述真实落地。
4. 常见问题包括同一实体多套主键、同名异义/同义异名、模式漂移、迟到乱序、重复投递、源端删除、历史回补、敏感数据越权和虚拟查询性能；措施可写主数据映射、Schema Registry、事件时间/水位线、幂等键、删除标记、分区回补、列级权限/脱敏、缓存和物化视图。
5. 效果用完整性、准确性、唯一性、及时性、规则通过率、端到端延迟、对账差异、回放成功率和下游查询时间衡量，并报告异常数据如何闭环。

## 试题三：论软件维护及其应用

请围绕“论软件维护及其应用”论题，依次从以下三个方面进行论述。

### 写作要求

1. 概要叙述你参与分析、设计的软件项目，以及你在其中所承担的主要工作。
2. 介绍软件维护的内容，以及提高可维护性的常见技术或方法。
3. 说明你在软件维护中遇到的问题、采用的技术手段及处理效果。

### 参考提纲

1. 对应要求 1，说明系统交付后的业务和技术背景、服务等级目标、历史债务及本人在变更评审、影响分析、发布、故障恢复或再工程中的职责。
2. 对应要求 2，维护内容可按改正性（修复缺陷）、适应性（适配环境/法规/依赖）、完善性（新增或改善功能/性能）、预防性（重构、消债、降低未来风险）组织。维护过程应包含问题/变更受理、分类优先级、影响分析、修改、验证、发布、配置基线和关闭复盘。
3. 提高可维护性的技术可分层写：架构上模块化、信息隐藏、高内聚低耦合、稳定接口和依赖隔离；代码上规范、重构、静态分析和复杂度控制；验证上单元/契约/回归测试及可重复环境；交付上版本控制、配置管理、CI/CD、灰度和回滚；运行上日志、指标、追踪、告警与故障手册；知识上架构决策记录、接口文档和交接机制。
4. 对应要求 3，选一到两个真实问题贯穿“现象和影响 → 定位证据 → 影响范围 → 技术决策及权衡 → 测试/发布 → 结果”。例如遗留模块耦合导致改一处坏多处，可先建立特征测试，再抽象接口和渐进重构；依赖升级不兼容可用适配层、契约测试、灰度和快速回滚。
5. 效果以平均恢复时间、变更前置时间、变更失败率、缺陷重开率、回归耗时、复杂度/重复率、覆盖率和发布频率的前后基线衡量；明确维护不等同于日常备份、值守等运行工作。

## 试题四：论面向服务的架构设计

请围绕“论面向服务的架构设计”论题，依次从以下三个方面进行论述。

### 写作要求

1. 概要叙述你参与分析、设计的软件项目，以及你在其中所承担的主要工作。
2. 论述基于 Web Service 的面向服务架构实现过程，以及 SOA 的哪些特征能够支撑软件功能复用。
3. 具体阐述你参与的软件项目如何以面向服务架构为指导实施，在实施过程中遇到了哪些问题，以及如何解决。

### 参考提纲

1. 对应要求 1，说明真实系统中的遗留应用、跨平台/跨组织集成需求、复用目标和本人承担的服务识别、契约、治理或平台工作。
2. 对应要求 2，可按“从业务能力/流程识别候选服务 → 确定边界、粒度和所有者 → 定义数据语义、WSDL 接口及策略契约 → 新建服务或用适配器封装遗留能力 → 部署并发布服务描述/注册信息 → 请求者发现或取得描述并绑定调用 → 用编排/事件组合服务 → 监控、版本、权限和 SLA 治理”描述实现过程。SOAP/HTTP 是常见消息/传输组合，不应把 SOA 等同于某一种协议。
3. 支撑复用的特征包括标准化、机器可读的显式契约和跨平台互操作；服务封装与松耦合，使请求者不依赖实现；按稳定业务能力划分的自治边界；可发现、可组合；无状态/幂等设计提升共享与扩展；统一策略、版本和运行治理控制复用风险。复用的对象是有清晰语义和服务等级的能力，而非简单把每个类包装成接口。
4. 对应要求 3，画清服务提供者、请求者、注册/目录、ESB 或网关及业务编排的数据流。问题可写服务粒度过细导致聊天式调用、共享数据耦合、契约版本破坏兼容、长事务、集中式 ESB 瓶颈、身份传递和端到端追踪；分别用领域/能力边界、聚合接口、契约优先与兼容演进、Saga/补偿、异步消息、横向扩展、统一身份与关联 ID 处理。
5. 效果用重复能力下线数、服务复用调用方数、集成周期、契约破坏次数、调用 P95、可用性、失败/补偿率和变更影响范围衡量，同时说明治理成本与分布式复杂性。
