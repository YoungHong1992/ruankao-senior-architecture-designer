## 试题一：论边缘计算及其应用

边缘计算是在靠近物或数据源头的网络边缘侧，融合网络、计算、存储、应用核心能力的分布式开放平台（架构），就近提供边缘智能服务。边缘计算与云计算各有所长，云计算擅长全局性、非实时、长周期的大数据处理与分析，能够在长周期维护、业务决策支撑等领域发挥优势；边缘计算更适用局部性、实时、短周期数据的处理与分析，能更好地支撑本地业务的实时智能化决策与执行。因此，边缘计算与云计算之间不是替代关系，而是互补协同关系，边云协同将放大边缘计算与云计算的应用价值。

请围绕“论边缘计算及其应用”论题，依次从以下三个方面进行论述。

### 写作要求

1. 概要叙述你参与管理和开发的软件项目以及你在其中所承担的主要工作。

2. 结合项目实际，概要说明六种边云协同，即资源协同、数据协同、智能协同、应用管理协同、业务管理协同、服务协同的含义。

3. 具体阐述你参与管理和开发的项目如何利用边缘计算进行设计与实现。

### 非官方参考提纲（原创摘要）

> **提纲证据强度：中。** 六类协同可由产业联盟白皮书交叉核对，但具体项目论述及考试评分没有官方答案。

1. 对应要求 1，说明真实场景为何需要在设备/现场附近处理数据，并交代端、边、云的数量级、时延/断网/隐私约束和本人负责的架构、部署或算法工作。
2. 对应要求 2，六种协同应逐项说清对象和方向：资源协同是云统一管理并按策略调度边缘的计算、存储、网络和设备；数据协同是边缘采集、预处理/过滤，云端汇聚、长期存储与分析；智能协同是云端集中训练和版本治理、边缘推理并回传样本/效果；应用管理协同是云端开发测试、发布与全生命周期管理，边缘提供运行环境；业务管理协同是云端按业务目标编排应用/数字孪生/网络实例，边缘执行实例；服务协同是云、边按时延和能力拆分 SaaS 服务并共同交付。
3. 对应要求 3，可按“终端/协议适配 → 边缘采集与本地规则/推理 → 消息缓冲和断点续传 → 云端存储、分析、训练 → 模型/配置灰度下发 → 边缘监控与回滚”展开。问题可写异构资源、弱网与时钟漂移、模型版本不一致、数据隐私、批量运维和边缘攻击面；措施对应资源画像与调度、离线自治、幂等去重、模型注册与签名、最小化上传、设备身份和远程证明等。
4. 结果使用端到端 P95 时延、上云流量削减比例、离线可用时长、模型更新成功率、边缘资源利用率、误报/漏报及故障恢复时间衡量，并解释测量窗口。

**资料依据（均访问于 2026-07-11）**

- [ECC/AII《边缘计算与云计算协同白皮书（2018 年）》公开 PDF 副本](https://13115299.s21i.faiusr.com/61/1/ABUIABA9GAAg4-iAjQYoi4O_4QY.pdf)（`B`）：第 2.1 节逐项定义资源、数据、智能、应用管理、业务管理和服务协同；文件署名为两联盟，但当前托管域名不是考试主管机构或联盟官网。
- [工业互联网产业联盟《时间敏感网络产业白皮书》官方 PDF](https://www.aii-alliance.org/upload/202002/0226_155046_929.pdf)（`B`）：其边云协同架构图独立列出同一组六类协同，可用于交叉核对名称和层次。

## 试题二：论多源数据集成及应用

在如今信息爆炸的时代，企业、组织和个人面临着大量的数据。这些数据来自不同的渠道和资源，包括传感器、社交媒体、销售记录等，它们各自具有不同的数据格式、分布和存储方式。因此，如何收集、整理和清洗数据，以建立一个一致、完整的数据集尤为重要。多源数据集成可以提供更全面的数据视角，将来自不同渠道的数据结合起来，通过这种方式整合多个数据源，从而减少单一数据源带来的误差和不准确性。此外，多源数据集成还可以帮助识别和矫正数据中的错误和重复项，提高数据质量。

请围绕“论多源数据集成及应用”论题，依次从以下三个方面进行论述。

### 写作要求

1. 概要叙述你参与管理和开发的软件项目以及你在其中所承担的主要工作。

2. 结合项目实际，详细说明多源数据集成的策略有哪些。

3. 具体阐述你参与管理和开发的项目如何基于多源数据集成进行设计与实现。

### 非官方参考提纲（原创摘要）

> **提纲证据强度：中。** 集成方式有公开标准和厂商技术资料支撑，但不存在可核验的官方考试答案或唯一分类。

1. 对应要求 1，列明真实数据源（数据库、文件、API、日志、消息或设备）、更新频率、数据量、使用方和本人负责的数据架构/治理工作，先说明集成目标而不是堆叠工具名。
2. 对应要求 2，可用四类互补策略组织：① 批量 ETL/ELT，将数据物化到仓库/湖仓；② 复制或 CDC，增量同步并维持近实时副本；③ 联邦查询/数据虚拟化，不搬移数据而提供统一逻辑视图；④ API、消息或流式集成，以服务契约和事件连接实时业务。再说明离线/实时、物化/虚拟、强一致/最终一致的选型边界。
3. 对应要求 3，可按“源盘点和元数据 → 统一业务术语/主数据与规范模型 → 连接器及全量基线 → CDC/消息增量 → 格式与语义映射 → 清洗、去重和实体匹配 → 质量规则与隔离区 → 血缘、权限和服务发布”描述。主要问题包括主键不一致、同名异义/同义异名、时间与编码差异、迟到乱序、模式演化、重复/脏数据、回补与隐私；分别用数据字典、映射规则、主数据、事件时间/水位线、Schema Registry、幂等键、对账和脱敏解决。
4. 结果用完整性、唯一性、准确性、及时性、规则通过率、数据延迟、对账差异、失败重放成功率和下游查询耗时衡量；不得仅以“数据量增加”代替质量效果。

**资料依据（均访问于 2026-07-11）**

- [W3C Recommendation：R2RML](https://www.w3.org/TR/2012/REC-r2rml-20120927/)（`A`）：提供关系模式到统一 RDF 词汇的可定制映射规范，支撑“模式/语义映射”环节。
- [IBM InfoSphere Information Server for Data Integration](https://www.ibm.com/products/information-server-for-data-integration)（`B`）：明确列出批量 ETL、虚拟/联邦和增量复制三种交付方式，可用于核对策略边界。

## 试题三：论面向对象的建模及应用

软件系统建模是软件开发中的重要环节，通过构建软件系统模型可以帮助系统开发人员理解系统，抽取业务过程和管理系统的复杂性，也可以方便各类人员之间的交流。软件系统建模是在系统需求分析和系统实现之间架起的一座桥梁，系统开发人员按照软件系统模型开发出符合设计目标的软件系统，并基于该模型进行软件的维护和改进。

请围绕“论面向对象的建模及应用”论题，依次从以下三个方面进行论述。

### 写作要求

1. 概要叙述你参与的软件系统开发项目以及你所担任的主要工作。

2. 说明什么是用例模型和分析模型以及你所参与的项目中是如何使用这两种模型的。

3. 详细说明你所参与的软件系统开发项目在使用用例模型和分析模型的过程中遇到哪些问题，是如何解决的。

### 非官方参考提纲（原创摘要）

> **提纲证据强度：中。** UML 元素及两类模型关系有 OMG 规范与 IBM 建模文档支撑，但项目写法和考试评分没有官方答案。

1. 对应要求 1，交代真实系统边界、主要参与者、复杂业务规则、本人承担的需求分析/建模/架构职责，以及模型服务的沟通和设计目标。
2. 对应要求 2，用例模型从外部视角描述系统“为谁提供什么价值”，包含参与者、用例、系统边界、关联以及必要的 `include`、`extend`、泛化关系，并以用例规约补充前置/后置条件、主成功场景、备选和异常流。分析模型从内部逻辑视角实现功能需求，通常用分析类、类图和序列图表达结构与协作；可用边界类、控制类、实体类分配职责，但不提前绑定数据库表或具体框架。
3. 在项目中先由访谈/工作坊形成参与者和业务目标，评审用例及验收条件；再逐个实现关键用例，识别分析类、职责和交互，建立“需求 → 用例 → 分析元素 → 设计/代码 → 测试”的追踪关系，并在迭代评审中同步更新。
4. 对应要求 3，可写用例粒度混乱、把界面步骤当业务目标、滥用 `include/extend`、遗漏异常流、分析模型过早设计化、跨用例职责重复、模型与代码漂移等问题；措施包括统一术语和模板、以用户目标控制粒度、场景走查、职责卡/边界-控制-实体分析、模型规则检查、追踪矩阵和版本化评审。效果可用需求覆盖率、模型缺陷、变更影响定位时间和验收遗漏数说明。

**资料依据（均访问于 2026-07-11）**

- [OMG Unified Modeling Language 2.5.1 规范页](https://www.omg.org/spec/UML/2.5.1)（`A`）：固定到 UML 2.5.1，提供 Actor、UseCase、Include、Extend 及结构/交互模型的规范基础。
- [IBM Rational Software Architect 9.7：模型类型与建模方法](https://www.ibm.com/docs/en/rational-soft-arch/9.7.0?topic=models-types-modeling-approaches)（`B`）：明确区分用例模型的外部行为与由类图、序列图表达的分析模型，并说明后者实现前者识别的功能需求。

## 试题四：论软件的可靠性评价

软件可靠性评价是软件可靠性活动的重要组成部分，既适用于软件开发过程，也可针对最终软件系统。在软件开发过程中使用软件可靠性评价，可以使用软件可靠性模型，估计软件当前的可靠性，以确认是否可以终止测试并发布软件，同时还可以预计软件要达到相应可靠性水平所需要的时间和工作量，评价提交软件时的软件可靠性水平。对于最终软件产品，软件可靠性评价结合可靠性验证测试，确认软件的执行与需求的一致性，确定最终软件产品所达到的可靠性水平。

请围绕“论软件的可靠性评价”论题，依次从以下三个方面进行论述。

### 写作要求

1. 概要叙述你参与开发的软件项目以及你在其中所承担的主要工作。

2. 说明可靠性模型有哪些，以及如何选择合适的可靠性模型。

3. 具体阐述你参与开发的项目如何对选用的可靠性模型进行分析来进行可靠性评价的。

### 非官方参考提纲（原创摘要）

> **提纲证据强度：中。** 模型类别、选择与检验原则有 NASA/NIST 一手资料支撑，但没有官方考试答案或指定模型。

1. 对应要求 1，说明真实系统的可靠性目标、运行剖面、测试阶段、失效采集方式及本人在可靠性计划、数据治理、建模或发布判定中的职责。
2. 对应要求 2，可先给出教材口径的十类：种子法、失效率类、曲线拟合、可靠性增长、程序结构分析、输入域、执行路径、非齐次泊松过程、马尔可夫过程、贝叶斯分析模型；再说明文献分类并不唯一，常见具体模型包括 Jelinski-Moranda、Musa/Musa-Okumoto、Goel-Okumoto NHPP、Duane/Weibull 增长和贝叶斯模型。
3. 选型不能只看模型名称，应逐项比较：模型假设是否符合缺陷发现/修复过程；输入需要失效间隔、累计失效数、执行时间还是运行剖面且能否可靠采集；输出能否回答当前可靠度、失效强度、MTTF/MTBF、剩余缺陷或达到目标所需时间；样本量、工具、计算与解释成本；对留出数据的拟合优度和预测误差。不存在适用于所有项目的唯一最佳模型。
4. 对应要求 3，可按“定义失效与运行剖面 → 清洗并按执行时间归一化数据 → 选多个候选模型 → 估计参数 → 用残差/趋势、拟合优度、似然或留出预测检验 → 计算指标及置信区间 → 与发布阈值比较 → 新数据到来后再校准”展开。必须记录修复是否立即且完美、测试强度是否稳定等假设，并做敏感性分析，避免把点预测当保证值。
5. 效果写真实的预测误差、置信区间、失效强度下降、达到阈值的测试时长和发布后失效情况；若模型检验未通过，应明确结论是“证据不足”而非强行发布。

**资料依据（均访问于 2026-07-11）**

- [NASA NTRS《Software Reliability Modeling》固定报告 PDF](https://ntrs.nasa.gov/api/citations/19820068865/downloads/19820068865.pdf)（`A`）：从日历时间、执行时间、贝叶斯、半马尔可夫、确定性和输入空间等角度展示模型分类，并说明失效/MTTF 等输出。
- [NIST/SEMATECH e-Handbook：检验可靠性模型假设](https://www.itl.nist.gov/div898/handbook/apr/section2/apr23.htm)（`A`）：要求用图形、拟合优度、似然比和趋势检验模型与数据的一致性，支撑候选模型比较和验证步骤。
