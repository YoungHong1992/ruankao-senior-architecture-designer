## 试题一：论基于构件的软件开发方法及其应用

基于构件的软件开发(Component-Based Software Development，CBSD)是一种基于分布对象技术、强调通过可复用构件设计与构造软件系统的软件复用途径。基于构件的软件系统中的构件可以是COTS(Commercial-Off-the-Shelf)构件，也可以是通过其它途径获得的构件(如自行开发)。CBSD将软件开发的重点从程序编写转移到了基于已有构件的组装，以更快地构造系统，减轻用来支持和升级大型系统所需要的维护负担，从而降低软件开发的费用。

请围绕“基于构件的软件开发方法及其应用”论题，依次从以下三个方面进行论述。

### 写作要求

1. 概要叙述你参与管理和开发的软件项目，以及你在其中所承担的主要工作。

2. 详细论述基于构件的软件开发方法的主要过程。

3. 结合你具体参与管理和开发的实际项目，请说明具体实施过程以及碰到的主要问题。

### 非官方参考提纲（原创摘要）

> **提纲证据强度：中。** CBSE 的过程与构件概念有一手技术报告支撑，但没有官方考试答案或评分映射。

1. 对应要求 1，先交代真实项目的业务目标、规模、约束及本人职责，并指出选择构件复用的动因，例如交付期、成熟能力复用、跨系统互操作或降低维护成本。
2. 对应要求 2，可按“需求概览 → 发现并鉴定候选构件 → 根据可用构件协商需求 → 选择构件模型并设计体系结构 → 定制/适配构件 → 组装、集成与系统验证 → 演化维护”展开。鉴定至少覆盖功能、接口、质量属性、许可、供应商持续性和运行环境；适配重点说明参数、操作名、数据格式、协议及非功能属性不匹配。
3. 对应要求 3，应把过程落到真实构件清单及接口上：自研与 COTS/开源构件如何取舍，怎样用适配器或胶水代码消除不匹配，怎样做契约测试、集成测试、性能/安全验证和版本治理。主要问题可围绕接口不兼容、构件黑盒可测性不足、依赖冲突、许可证与供应链风险、升级破坏兼容性展开，并给出对应措施。
4. 结果只写可核验指标，例如复用比例、交付周期、缺陷密度、集成失败率、升级耗时和回滚次数；同时说明复用带来的约束，避免只写优点。

**资料依据（均访问于 2026-07-11）**

- [CMU/SEI《C4 Software Technology Reference Guide》](https://resources.sei.cmu.edu/asset_files/Handbook/1997_002_001_16523.pdf)（`A`）：给出构件鉴定、适配、组装和演化四项活动，可用于校验上述过程主线。
- [CMU/SEI-2000-TR-008《Technical Concepts of Component-Based Software Engineering》](https://www.sei.cmu.edu/library/volume-ii-technical-concepts-of-component-based-software-engineering-2nd-edition/)（`A`）：界定构件、接口、契约、构件模型、框架、组合与认证等核心概念。

## 试题二：论软件维护方法及其应用

软件维护是指在软件交付使用后，直至软件被淘汰的整个时间范围内，为了改正错误或满足新的需求而修改软件的活动。在软件系统运行过程中，软件需要维护的原因是多种多样的。根据维护原因不同，可以将软件维护分为改正性维护、适应性维护、完善性维护和预防性维护。在维护过程中，也需要对软件的可维护性进行度量。在软件外部，一般采用 MTTR 来度量软件的可维护性；在软件内部，可以通过度量软件的复杂性来间接度量软件的可维护性。

据统计，软件维护阶段占整个软件生命周期 60% 以上的时间。因此，分析影响软件维护的因素，度量和提高软件的可维护性，就显得十分重要。

请围绕“软件维护方法及其应用”论题，依次从以下三个方面进行论述。

### 写作要求

1. 概要叙述你参与管理和开发的软件项目，以及你在其中所承担的主要工作。

2. 详细论述影响软件维护工作的因素有哪些。

3. 结合你具体参与管理和开发的实际项目，说明在具体维护过程中，如何度量软件的可维护性，说明具体的软件维护工作类型。

### 非官方参考提纲（原创摘要）

> **提纲证据强度：中。** 维护分类、过程和关键问题有 ISO/IEEE 及 SWEBOK 依据，但没有官方考试答案或评分映射。

1. 对应要求 1，说明系统已交付后的业务背景、技术栈、用户规模、服务等级目标及本人在变更评审、影响分析、发布或故障恢复中的职责。
2. 对应要求 2，可把影响因素分成四组：产品因素（规模、复杂度、耦合、文档、测试覆盖、技术债）；变更因素（需求清晰度、影响范围、紧急度、外部接口/法规变化）；过程与工具因素（配置基线、变更控制、自动化测试、CI/CD、监控与回滚）；人员与组织因素（知识传承、人员流动、技能、供应商与跨团队协作）。说明这些因素如何影响可分析性、可修改性、可测试性和恢复速度。
3. 对应要求 3，外部度量可选平均恢复时间、变更前置时间、变更失败率、缺陷重开率和发布/回滚次数；内部度量可选圈复杂度、耦合/内聚、重复率、覆盖率、静态检查债务和文档完整率。再把真实工作分别归入改正性、适应性、完善性、预防性维护，并用一次完整变更说明“受理 → 分类与影响分析 → 修改 → 回归/验收 → 发布 → 复盘与基线更新”。
4. 应区分“恢复服务的 MTTR”和“彻底修复缺陷的周期”，并说明统计口径、观察窗口和基线，否则单个数字没有可比性。

**资料依据（均访问于 2026-07-11）**

- [ISO/IEC/IEEE 14764:2022 软件维护过程](https://www.iso.org/standard/80710.html)（`A`）：规定软件维护过程、活动、任务及维护类型的标准依据。
- [IEEE Computer Society SWEBOK v4 软件维护主题目录](https://www.computer.org/education/bodies-of-knowledge/software-engineering/topics)（`A`）：列出技术、管理、成本、度量、过程、再工程、逆向工程和持续交付等维护知识点。

## 试题三：论区块链技术及应用

区块链作为一种分布式记账技术，目前已经被应用到了资产管理、物联网、医疗管理、政务监管等多个领域。从网络层面来讲，区块链是一个对等网络(Peer to Peer，P2P)，网络中的节点地位对等，每个节点都保存完整的账本数据，系统的运行不依赖中心化节点，因此避免了中心化带来的单点故障问题。同时，区块链作为一个拜占庭容错的分布式系统，在存在少量恶意节点情况下可以作为一个整体对外提供稳定的服务。

请围绕“区块链技术及应用”论题，依次从以下三个方面进行论述。

### 写作要求

1. 概要叙述你参与管理和开发的软件项目以及你在其中所承担的主要工作。

2. 区块链包含多种核心技术，请简要描述区块链的3种核心技术。

3. 具体阐述你参与管理和开发的项目是如何应用区块链技术进行设计与实现。

### 非官方参考提纲（原创摘要）

> **提纲证据强度：中。** 核心技术及工程风险有 NIST 政府技术报告支撑，但具体项目论述和考试评分没有官方答案。

1. 对应要求 1，说明为何业务需要多方共同记账、参与方之间为何不能完全互信、传统中心化数据库为何不足，并交代本人负责的链型选择、合约/接口、安全或部署工作。若单一组织数据库即可解决，应如实说明不宜使用区块链。
2. 对应要求 2，可选择并贯通三项核心技术：① 哈希链、Merkle 结构、非对称密码与数字签名，提供完整性、身份与不可抵赖基础；② P2P 网络和多副本分布式账本，传播并保存一致记录；③ 共识机制，在故障或恶意节点存在时确定交易顺序和有效状态。智能合约可作为受确定性约束的业务规则执行层补充说明。
3. 对应要求 3，可按“许可链参与方与证书体系 → 账本/通道或隐私域 → 交易与背书规则 → 共识与排序 → 智能合约 → 链上索引、链下大对象及哈希锚定 → 业务系统 API → 监控审计”描述。问题应覆盖吞吐/确认时延、隐私泄露、密钥丢失、错误数据上链、合约升级、节点治理和与存量系统一致性，并说明批量提交、权限分层、密钥托管、合约测试、版本治理、幂等与补偿等措施。
4. 效果可用确认时延、吞吐量、对账耗时、争议数、审计取证时间和节点故障恢复结果衡量；“不可篡改”应表述为篡改可检测且受共识/权限约束，不能写成绝对无法改变。

**资料依据（均访问于 2026-07-11）**

- [NISTIR 8202《Blockchain Technology Overview》发布页](https://www.nist.gov/publications/blockchain-technology-overview)（`A`）：系统说明哈希、非对称密码、交易、区块、P2P 网络、共识、许可模型及智能合约。
- [NISTIR 8202 固定报告 PDF](https://nvlpubs.nist.gov/nistpubs/ir/2018/NIST.IR.8202.pdf)（`A`）：可按报告号和页码复核概念、限制与实施注意事项。

## 试题四：论湖仓一体架构及其应用

随着 5G、大数据、人工智能、物联网等技术的不断成熟，各行各业的业务场景日益复杂，企业数据呈现出大规模、多样性的特点，特别是非结构化数据呈现出爆发式增长趋势。在这一背景下，企业数据管理不再局限于传统的结构化 OLTP（On-Line Transaction Processing）数据交易过程，而是提出了多样化、异质性数据的实时处理要求。传统的数据湖（Data Lake）在事务一致性及实时处理方面有所欠缺，而数据仓库（Data Warehouse）也无法应对高并发、多数据类型的处理。因此，支持事务一致性、提供高并发实时处理及分析能力的湖仓一体（Lake House）架构应运而生。湖仓一体架构在成本、灵活性、统一数据存储、多元数据分析等多方面具备优势，正逐步转化为下一代数据管理系统的核心竞争力。

请围绕“湖仓一体架构及其应用”论题，依次从以下三个方面进行论述。

### 写作要求

1. 概要叙述你参与管理和开发的、采用湖仓一体架构的软件项目以及你在其中所承担的主要工作。

2. 请对湖仓一体架构进行总结与分析，给出其中四类关键特征，并简要对这四类关键特征的内涵进行阐述。

3. 具体阐述你参与管理和开发的项目是如何采用湖仓一体架构的，并围绕上述四类关键特征，详细论述在项目设计与实现过程中遇到了哪些实际问题，是如何解决的。

### 非官方参考提纲（原创摘要）

> **提纲证据强度：中。** 四类特征由 CIDR 2021 原始论文综合归纳，属于可复核技术提纲，不是官方考试答案。

1. 对应要求 1，交代真实数据来源、规模、时效、分析类型和旧架构痛点，并说明本人承担的数据架构、表格式/计算引擎选型、治理或迁移职责。
2. 对应要求 2，可选四类相互区分的特征：① 低成本、可直接访问的开放数据格式，结构化、半结构化和非结构化数据共用底座；② 事务元数据层提供 ACID、版本、审计、模式约束和治理；③ 存算分离，多种计算集群按需独立扩缩并访问同一份数据；④ 同时支持 BI/SQL、流批处理、数据科学和机器学习，并通过缓存、索引、统计信息与查询优化获得可用性能。
3. 对应要求 3，应画清“源系统/CDC 与文件 → 对象存储或 HDFS 的开放表格式 → 事务元数据/目录与权限 → 流批计算和 SQL/ML 引擎 → 数据服务”的数据流。问题可分别对应四类特征：并发写冲突和小文件、模式漂移与脏数据、冷热资源争用、查询性能和流批一致性；措施可写乐观并发与幂等、压缩/合并、模式演化与质量门禁、工作负载隔离、分区/聚簇/缓存、检查点和水位线。
4. 用数据新鲜度、失败重跑率、重复存储量、查询 P95、单位数据成本、资源利用率和模型取数周期等真实指标说明效果，并保留开放格式、事务能力和性能之间的权衡。

**资料依据（均访问于 2026-07-11）**

- [Armbrust 等，CIDR 2021《Lakehouse: A New Generation of Open Platforms that Unify Data Warehousing and Advanced Analytics》](https://www.vldb.org/cidrdb/papers/2021/cidr2021_paper17.pdf)（`A`）：原始论文明确开放直读格式、机器学习/数据科学支持、SQL 性能，以及事务元数据层、治理、版本和存算分离等设计依据。
