## 试题一：论 Serverless 架构模式

随着云计算技术的迭代与微服务架构的普及，企业对 IT 系统的弹性伸缩、成本优化及运维效率提出了更高要求：既需快速响应业务峰值需求，又需降低闲置资源消耗，同时减少基础设施运维负担。Serverless（无服务器）架构通过函数即服务（FaaS）与后端即服务（BaaS），实现按需分配资源、按使用付费及减少底层运维负担，适用于 API 服务、事件驱动应用和定时任务等场景。

请围绕“Serverless 架构模式”论题，依次从以下三个方面进行论述。

### 写作要求

1. 概要叙述你参与管理和开发的软件项目，以及你在其中所担任的主要工作。
2. 详细论述 Serverless 架构模式的核心组成部分及各部分的作用，并说明这些组成部分如何协同实现降本增效和弹性伸缩。
3. 结合你参与的项目，说明 Serverless 架构方案的选型依据、落地过程中的关键挑战及应对措施，以及实际应用效果。

### 非官方参考提纲（原创摘要）

> **提纲证据强度：中。** Serverless 概念和平台构成可由 CNCF 白皮书固定版本核对，但该题没有官方答案或评分映射。

1. 对应要求 1，说明真实负载是否事件驱动、峰谷是否明显、单次执行时长和状态特点，以及本人负责的架构选型、函数拆分、平台工程、安全或成本治理工作。先论证适用性：长时间密集计算、强本地状态、持续低时延或频繁服务间调用可能不适合纯 FaaS。
2. 对应要求 2，可分四组组件：① 事件源/API 网关/消息与定时触发，接入请求并解耦生产者；② FaaS 控制面与运行时，负责函数版本、调度、隔离、实例创建、并发和自动伸缩；③ BaaS，如托管身份、数据库、对象存储、消息和工作流，承载持久状态与通用后端能力；④ 交付与治理面，包括 IaC/CI/CD、IAM、密钥、日志指标追踪、计量和告警。
3. 协同链路写成“事件进入 → 网关认证/限流或消息缓冲 → 平台选择函数版本并按并发创建实例 → 函数执行无状态业务并访问 BaaS → 结果/事件驱动后续步骤 → 遥测与计量闭环”。没有请求时缩容、峰值按并发扩容，结合按调用/资源时长计费减少闲置；托管能力减少基础设施运维，但并不等于零运维或一定更便宜。
4. 对应要求 3，选型比较流量形态、延迟 SLO、执行/内存限制、状态与事务、生态兼容、合规、可移植性和总成本。挑战可写冷启动、并发突增压垮下游、至少一次投递、状态外置、可观测性、权限蔓延、厂商锁定和成本失控；措施包括预置并发/分层缓存、队列背压与并发上限、幂等键/去重、工作流状态机、统一追踪、最小权限、适配层及预算告警。
5. 效果用冷/热启动 P95、峰值并发、错误/重试率、扩容时间、下游饱和度、单位请求成本、闲置成本和发布频率衡量，提供迁移前后同口径数据。

## 试题二：论基于云原生数据库的企业信息系统架构设计

随着云原生技术的普及，企业信息系统对弹性伸缩、高可靠性、资源高效利用及敏捷迭代能力提出了更高要求。传统数据库的存储与计算耦合、扩展能力受限、运维成本高和故障恢复慢等问题，可能难以适配现代企业业务。云原生数据库融合容器化部署、Kubernetes 编排、存储与计算分离、可观测性等技术，以适应云环境中的资源按需分配、故障自愈和全链路监控需求。

请围绕“论基于云原生数据库的企业信息系统架构设计”论题，依次从以下三个方面进行论述。

### 写作要求

1. 概要叙述你参与管理和开发的企业信息系统项目，以及你在其中所担任的主要工作。
2. 详细论述云原生数据库的核心技术优势，以及架构设计中如何体现云原生数据库的技术特性。
3. 结合你参与的项目，说明基于云原生数据库的架构选型依据、落地过程中的关键难点及应对措施，以及最终架构的实施效果。

### 非官方参考提纲（原创摘要）

> **提纲证据强度：中。** 云原生和状态工作负载的特征有 CNCF、Kubernetes 与数据库项目官方资料支撑，但没有官方考试答案或唯一产品架构。

1. 对应要求 1，说明真实系统的事务/分析负载、数据规模、峰谷、RPO/RTO、合规边界及旧数据库瓶颈，并交代本人负责的选型、数据分层、迁移、容灾或数据库平台工作。
2. 对应要求 2，核心优势可围绕：计算与存储或 SQL 层与分布式存储解耦，按瓶颈独立横向扩展；多副本、故障检测和自动切换提高可用性；声明式编排/Operator 自动化部署、升级、备份和恢复；资源池化与按需调度提高利用率；日志、指标、追踪和审计形成可观测与治理闭环；标准接口、容器/IaC 和自动化交付支持可移植与敏捷迭代。
3. 架构可画成“接入/代理与服务发现 → 无状态或可扩展 SQL/计算节点 → 事务协调/元数据 → 分片多副本存储 → 对象存储备份/日志归档”，旁路配置 Operator、伸缩、监控告警、密钥、审计和灾备。Kubernetes `StatefulSet` 只提供稳定身份、持久卷关联和有序更新，不自动提供数据库一致性、选主、备份或跨区容灾；这些必须由数据库/Operator 负责。
4. 对应要求 3，选型需比较 SQL/协议兼容、事务隔离、一致性、TP/AP/HTAP、延迟与吞吐、扩缩容方式、地域容灾、迁移工具、可观测性、锁定风险和 TCO。难点可写全量+增量迁移和切换、热点分片、扩容重平衡、连接风暴、故障误切换、备份可恢复性、版本升级；措施包括 CDC 对账与灰度双读、合理分区/散列、连接池和限流、仲裁与故障演练、PITR 恢复演练、兼容性测试及回滚。
5. 效果用查询/事务 P95、TPS/QPS、扩容耗时、故障切换 RTO、数据丢失 RPO、恢复演练成功率、资源利用率、单位事务成本和发布停机时间衡量，不使用未经实测的“零丢失”“秒级自愈”。

- [Kubernetes：StatefulSets](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/)（`B`）：明确稳定网络标识、持久存储和有序伸缩/更新的能力与限制，支撑上述边界说明。

## 试题三：论系统的性能测试

随着互联网应用规模扩大、业务场景复杂化，响应延迟、并发处理能力不足和资源耗尽等问题会影响用户体验与业务连续性。性能测试通过模拟业务负载，验证系统的响应速度、吞吐量、稳定性等指标，并帮助发现性能瓶颈。

请围绕“性能测试”论题，依次从以下三个方面进行论述。

### 写作要求

1. 概要叙述你参与管理和开发的软件项目，以及你在其中所担任的主要工作。
2. 详细论述性能测试的核心类型（如负载测试、压力测试、并发测试等）、关键指标（如响应时间、吞吐量、资源利用率等）及核心流程，并说明各环节如何协同实现性能达标验证和性能瓶颈定位。
3. 结合你参与的项目，说明性能测试方案的设计依据、落地过程中的关键挑战及应对措施，以及测试后的优化效果。

### 非官方参考提纲（原创摘要）

> **提纲证据强度：中。** 测试类型、负载模型和用户侧性能量值有 ISTQB/ISO 公开资料支撑，但具体项目与评分没有官方答案。

1. 对应要求 1，说明真实系统关键业务链路、用户/交易峰值、性能 SLO、部署拓扑、本人负责的容量模型、脚本、监控、分析或调优工作。
2. 对应要求 2，核心类型可写：负载测试验证预期并发/吞吐下的达标能力；压力测试超过上限或减少资源以寻找失效点与恢复行为；并发测试关注同时访问引发的锁、竞态和资源争用；峰值/突发测试验证骤升骤降；耐久测试发现泄漏和长期退化；容量/可扩展性测试确定数据量、用户数和扩容边界。每种测试都应对应一个问题，不能只换并发数名称。

5. 对应要求 3，挑战可写测试环境偏差、数据/缓存不真实、负载发生器成为瓶颈、思考时间和到达率模型错误、监控缺口、第三方限流、结果波动；措施包括环境差异清单与校准、脱敏生产分布数据、分布式压测机自监控、预热与多轮置信区间、依赖桩/配额协调及固定版本配置。优化效果必须以相同脚本、数据、环境和负载模型的前后对比证明，并确认功能/稳定性未回退。

## 试题四：论秒杀场景及其技术解决方案

秒杀是电子商务领域典型的高并发、短时效业务场景，具有瞬时流量峰值高、业务逻辑集中和数据一致性要求严格等特点。传统架构可能出现响应超时、库存超卖和服务雪崩等问题。扩容、动静分离、缓存、服务降级与限流等手段可通过分流、提速、减压和兜底协同应对高并发。

请围绕“论秒杀场景及其技术解决方案”论题，依次从以下三个方面进行论述。

### 写作要求

1. 概要叙述你参与管理和开发的秒杀相关软件项目，以及你在其中所担任的主要工作。
2. 详细论述秒杀场景的核心技术挑战，分别说明扩容、动静分离、缓存、服务降级、限流等技术的实现方法，以及这些技术如何协同解决高并发问题。
3. 结合你参与的项目，说明秒杀技术解决方案的选型思路、落地过程中的关键难点及应对措施，以及最终的技术实施效果。

### 非官方参考提纲（原创摘要）

> **提纲证据强度：中。** 高并发治理手段有云厂商官方工程资料交叉支撑，但它们是工程参考，不是官方考试答案，也不能替代真实项目数据。

1. 对应要求 1，说明真实活动的 SKU/库存、预测峰值、持续时间、渠道、订单链路、一致性与公平要求，以及本人负责的容量、流量、库存、消息或稳定性工作。
2. 核心挑战包括瞬时读写洪峰、有效请求占比极低、库存超卖/少卖、热点键与数据库锁竞争、重复/机器人请求、下游支付或订单服务抖动、队列积压和故障级联。先用业务容量模型确定“允许进入核心链路的最大速率”，再组合技术而不是无上限扩容。
3. 扩容：应用无状态化、水平扩展、活动前预热并压测数据库/缓存/消息的真实上限；动静分离：商品页和静态资源提前生成并由浏览器/CDN 承接，只让下单进入动态链路；缓存：预热活动状态和可售库存，用原子条件扣减/脚本防止负数，并与数据库订单、超时释放和对账闭环；服务降级：关闭推荐、评论等非核心能力，提供缓存/占位返回并用熔断隔离故障；限流：在 CDN/WAF、网关、用户/设备/SKU 和服务层采用令牌桶/漏桶或并发上限，售罄后尽早拒绝。
4. 协同链路可写“CDN 吸收浏览流量 → 网关鉴权、防刷、限流 → 缓存原子预扣/资格校验 → 有界消息队列削峰 → 订单消费者以幂等键持久化 → 支付成功确认或超时补偿库存 → 对账修复”。队列必须有容量、过期、死信和背压策略；无限排队会让过期请求继续消耗系统。
5. 对应要求 3，选型依据包括峰值与库存比、可接受排队时长、一致性/公平、依赖容量、恢复目标和成本。难点可写缓存与数据库双写、重复消费、库存回补、热点分片、恶意流量、扩容不及时和降级误触发；用状态机、唯一约束、幂等/去重、补偿与周期对账、热点隔离、签名/验证码、预扩容和演练解决。
6. 效果用入口峰值、核心链路放行率、下单 P95/P99、库存差异/超卖数、消息积压与清空时间、错误率、降级时长、资源水位和单位成功订单成本衡量，同时报告失败与恢复结果。
